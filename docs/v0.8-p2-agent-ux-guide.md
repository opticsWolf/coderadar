## 2. Findings (root causes, verified against source)

### F1 — Multi-token search is structurally empty (P2-1)

`search_entities` (core_indexer/src/lib.rs:1294) builds one lowercase string
from the whole query; `name_score` (lib.rs:1271) then scores each entity name
as exact / prefix / contains against that **whole string**. Two or more
whitespace-separated tokens almost never appear verbatim inside one identifier,
so every multi-token query returns nothing regardless of index state. `codegraph_explore`
is unaffected because it tokenizes first (`_parse_names` → `_resolve_names`,
mcp/server.py:2511 — one single-token `_text_search` per candidate name);
`codegraph_search` is the discovery tool, which is precisely the one that
fails.

**Fix (P2-1):** score per token, OR semantics, summed. One entity's score is
the kind-weight × sum of per-token contributions: name tiers 100/50/25
(exact/prefix/contains), signature 10, docstring 5. A single-token query gets
the identical behavior it has today (one contribution) except that
signature/docstring are included additively at the low tiers — an additive
change that cannot demote an exact/prefix/contains name match. Empty results
gain a helpful tail (P2-6).

### F2 — `create_entity` cannot render real signatures (P2-2)

`_render_entity_code` (mcp/server.py:2217) has no parameter channel; Rust
renders `pub fn {name}() {`. The MCP schema (`coderadar_create_entity`) exposes
`file_path, language, kind, name, body, decorators, anchor, dry_run` — no way
to say `fn sync_status_text(store: &Store) -> String`.

**Fix (P2-2):** optional `signature` parameter on the tool; when present, it is
used verbatim as the function/method head (the renderer is bypassed for
function-like kinds), when absent the legacy rendering is unchanged. Tool
description updated: default rendering is for parameter-less helpers; pass
`signature` for anything real.

### F3 — Project binding does not survive process restarts (P2-3)

By design the MCP server process is disposable ("the server is a disposable
process; state lives only in it", mcp/lifecycle.py). The startup ladder
(mcp/roots.py) has no memory of an explicit `codegraph_set_project` from a
previous session, so a restarted client re-discovers the marker project (or
asks for roots) and the agent must re-switch.

**Fix (P2-3):** a small per-user state file
(`~/.coderadar/mcp/last_projects.json`) mapping **launch-cwd → last explicitly
selected root**. `codegraph_set_project` writes it; `mcp serve` consults it as
a new ladder rung — below `--path`, above markers/cwd — *only when the
recorded directory still exists* (validation, since the record can go stale),
and reports the resume in the startup line ("resumed project X from your last
session"). An explicit `--path` always wins; a `set_project` to a different
project overwrites the record. The `LazyRootRetry` client-roots flow is
untouched — client-declared roots remain the top rung.

### F4 — Project switch (and startup) always re-indexes from scratch (P2-4)

`BackgroundIndex._run` (mcp/startup.py) calls `coderadar.analyze(self.root)`
unconditionally. The CLI path already does better after v0.8 P1:
`_ensure_graph` (cli.py:184) reuses a fresh store via `coderadar.load` and
falls back to `analyze` only when the store is missing/stale
(`_store_is_fresh`, cli.py:154).

**Fix (P2-4):** factor the CLI staleness machinery (`_store_db_path`,
`_store_is_fresh`, `_INDEXABLE_EXTS`, skip dirs, and the load-else-analyze
decision) into a shared helper module and call it from the background index:
fresh store → `coderadar.load(db, root)` + `update_file` for each stale file;
no store/stale store → `analyze(root, create_store=True)` (which also
rebuilds/refreshes the store for next time). This makes startup and
`codegraph_reindex` sub-second on a warm repo, and gives the E9 "manual edit"
case a cheap, precise refresh instead of a re-switch.

### F5 — Call sites inside macro bodies are invisible to the call graph (P2-5)

tree-sitter's Rust grammar desugars macro invocations to
`macro_invocation → token_tree`; the extractor visits real syntax nodes, so
calls inside `rsx! { … }`, `quote! { … }` etc. are never collected into
`Function.calls`, never resolved, and never enter `callers_by_callee`.
`plan_signature_update` / `plan_rename` (core_indexer/src/mutation/mod.rs:502)
enumerate sites *from the graph*, so the plan is silently incomplete — the
exact E5 symptom.

**Fix (P2-5):** a language-agnostic **textual backstop** in the mutation
planners: after the structural enumeration, scan the indexed source files for
occurrences of `{name}(` (word-boundary match) and append occurrences not
already covered by a graph call site as *unverified sites* labelled "textual
occurrence — may be inside a macro body, comment or string; check manually".
Output is capped (first 15) so it stays a starting point, not a flood. No
macro expansion, no new grammars (non-goal).

### F6 — Entity-ID separators (P2-6, note only)

IDs are FK-stable and stay OS-native. Nothing to change in this round; the
search/mutation output already shows `file_path` alongside the ID, and the
tool descriptions keep IDs as the canonical handles. (If it ever matters, the
display layer can normalise to `/` without touching stored IDs.)

## 3. Change specs

### P2-1 — Multi-token search (Rust, `core_indexer/src/lib.rs`) — status: DONE

**Where:** `search_entities` (~line 1294) + `name_score` (~line 1271).

**Spec:**
1. Tokenize the query on whitespace; dedupe tokens, keep order; strip
   surrounding `(){}[]<>,;"'` punctuation from each token.
2. Per entity, per token, compute:
   - name tier: 100 exact, 50 prefix, 25 contains (against the lowercased
     entity name — the existing tiers, verbatim);
   - signature: 10 if the token occurs in the lowercased `signature` string
     (functions/methods only, when non-empty);
   - docstring: 5 if the token occurs in the lowercased `docstring`
     (when non-empty).
3. Entity score = kind weight × (sum over tokens). Zero if no token scores.
   (A single-token query therefore scores exactly as today plus the additive
   signature/docstring tiers — exact/prefix/contains name matches are never
   demoted.)
4. Ranking, `kind` filter, `top_k` truncation, and the returned dict shape are
   unchanged.

**Tests:** new `tests/test_search_multitoken.py` (9 tests, Python, real
fixture project through `analyze`): two tokens → two entities; multi-token
entity outranks single-token one; signature-only and docstring-only tokens
returned; single-token exact match stays first; kind filter composes; empty
query keeps the enumeration contract; short tokens skip low tiers.

**Post-implementation notes (discovered while implementing):**
1. **`Function.docstring` was always None for in-body docstrings.** The
   extractor's `pending_docstring` field (single_pass.rs) was set by the
   `Tag::Docstring` capture and never read — and `preceding_docstring` only
   reaches text *before* a declaration (Rust `///`), never a Python docstring
   *inside* the body. The docstring tier of the new scorer was therefore
   dead on arrival for Python. Fixed with a backfill in the `Tag::Docstring`
   dispatch: the in-body string statement fires *after* its unit is emitted
   (preorder), so the tag now writes the docstring onto the current function
   unit when the line range is inside it and the field is still empty. Also
   stripped Python `"""` delimiters in `emit_docstring_node`. (Class docstrings
   still need a class-index analogue — out of scope, noted.)
2. **The empty-query enumeration contract.** The old whole-string scorer gave
   `""` a prefix hit on every name, so `search_entities("", top_k, kind)`
   was the codebase's "enumerate all of kind" call (the visualizers'
   `_entities_of_kind` is built on it). The first tokenized version returned
   `[]` for empty queries and silently broke every DOT/mermaid diagram
   (`No classes in the index`). The scorer now scores every entity 1 for an
   empty token list, preserving the contract. Lesson: the search path is a
   shared enumeration facility, not just a query engine.
3. **Build trap:** `cargo test --release` does not rebuild the cdylib; the
   Python suite runs against `target/release/core_indexer.dll` copied to
   `_core.pyd`. Always `cargo build --release` before the copy.

### P2-3 — Project persistence across sessions (Python, `cli.py` + `mcp/`) — status: DONE

**Where:** new `py_agent/src/coderadar/project_state.py`; `cli.py` `mcp serve`
start; `_set_project` in `mcp/server.py`.

**Spec:**
1. `project_state.py`: `record_project(launch_cwd: Path, root: Path)` and
   `last_project_for(launch_cwd: Path) -> Optional[Path]`. File:
   `~/.coderadar/mcp/last_projects.json` = `{ "<normalized launch cwd>":
   "<root>" }`. Writes are best-effort (never raise into the tool path);
   reads validate that the recorded directory still exists.
2. `mcp serve` (cli.py ~line 803): capture the **pre-adopt cwd** (the client's
   launch directory) before `adopt_project_root` chdirs; after the
   `--path`-check, before the marker/cwd ladder, consult
   `last_project_for(launch_cwd)` — if present, use it as a confirmed
   `ResolvedRoot(source="previous session")`. The startup log line names the
   resume.
3. `_set_project`: after a successful switch, `record_project(launch_cwd,
   new_root)`. The launch cwd is captured once at server construction
   (`os.getcwd()` in `serve`, before any chdir) and passed in.
4. `--path` always beats the record (explicit operator intent). A `set_project`
   back to the marker project also rewrites the record (last explicit choice
   wins, whatever it is).

**Tests:** `tests/mcp/test_project_state.py` — record/read round-trip; stale
record (deleted dir) returns None; `mcp serve` subprocess smoke: seed a record
for a cwd, launch with that cwd, assert the startup line contains "previous
session" and the right root; `--path` to another marked project wins.

### P2-4 — Incremental cold start for startup/switch/reindex (Python) — status: DONE

**Where:** new `py_agent/src/coderadar/coldstart.py` (factored from cli.py:
`_INDEXABLE_EXTS`, `_STALENESS_SKIP_DIRS`, `_store_db_path`,
`_store_is_fresh`); `mcp/startup.py` `BackgroundIndex._run`; `cli.py`
`_ensure_graph` (refactored to call the shared helper — behavior unchanged).

**Spec:**
1. `coldstart.build_graph(root: Path, create_store: bool = True) -> CodeGraph`:
   - `db = <root>/.coderadar/store/coderadar.db`;
   - if `db` exists and `_store_is_fresh(root, db)`: `coderadar.load(db,
     str(root))`, then `update_file` each stale file (files newer than the
     db, same skip rules) — the update keeps the store and graph in sync;
   - else `coderadar.analyze(str(root), create_store=create_store)`.
2. `BackgroundIndex._run` calls `build_graph(Path(self.root))` instead of
   `analyze` directly. Same exception contract (the index thread records the
   error; `ensure_ready` surfaces it as before).
3. `cli.py::_ensure_graph` delegates to `coldstart` (single implementation of
   the staleness rules; the CLI's load/analyze fallback ordering is preserved).

**Tests:** `tests/test_mcp_coldstart.py` — fixture repo analyzed once (store
exists); age one source file; `build_graph` returns a graph where the aged
file's entities are refreshed (mtime-driven `update_file` ran) while a
second, untouched file's entities come from the store (verified by a marker
string that exists only in the old store copy, plus `graph_stats()` revision
== store revision); no-store dir → analyze path; stale-store dir (db older
than a new file… covered by the aged-file case; plus a corrupt/foreign db is
not attempted when `_store_is_fresh` is false).

### P2-5 — Textual call-site backstop in mutation planners (Rust, `core_indexer/src/mutation/mod.rs`) — status: DONE (see post-implementation notes)

**Where:** `plan_signature_update` (~line 502) and `plan_rename` (same file);
shared helper in the module.

**Spec:**
1. `fn textual_occurrences(projection: &ProjectedGraph, name: &str) -> Vec<(String /*file*/, u32 /*line*/, String /*snippet*/)>`:
   for each file of each module in the projection, read the source (cached
   per file), find line-start or any-position matches of `name` followed by
   `(` with a word boundary before it; skip the definition line of the entity
   itself; cap at 15 results.
2. In both planners, after the structural site enumeration: for each textual
   occurrence not already covered by a graph call site (same file + line,
   ±1 tolerance), append an `UnverifiedSite` with reason `"textual occurrence
   — may be inside a macro body, comment or string; check manually"` and the
   line's trimmed source as snippet.
3. Plan output formatting already renders unverified sites
   (`_format_mutation_plan`), so the MCP side needs no change.

**Tests:** Rust unit test (fixture module): a function called directly and a
call inside a `macro! { … name( … ) }`-style token body — the direct site is a
graph site, the macro one appears only as an unverified textual site. Python
integration: `plan_signature_update` on such a fixture lists both, with the
macro one flagged.

## 4. Non-goals

- Root-relative entity IDs / multi-project serving (single-project core;
  documented in mcp/lifecycle.py).
- Parsing macro bodies (`rsx!`/`quote!`) — the P2-5 backstop reports, it does
  not parse.
- Indexing external dependencies (E8) — out of scope by design.
- Changing stored entity-ID format (FK stability, §F6).
- Anything touching the v0.8 P1 ledger/cold-start contracts (P2-4 *reuses*
  them, never changes them).

**P2-4 post-implementation notes:**
1. **`create_store` defaults to False, not the True in the spec.** Only
   `coderadar init` plants the `.coderadar/` marker (see `analyze`'s
   docstring): a background index that created it would make a wrong root
   guess self-confirming. The MCP startup path keeps its pre-P2-4
   `create_store=False` behavior.
2. **`build_graph` loads whenever the store exists** — `store_is_fresh`
   only gates the stale-file scan (fast path), not the load itself. Under
   the spec's literal reading (load only when fresh), the "load + update
   stale files" branch would be unreachable, since a stale file is exactly
   what makes `store_is_fresh` false.
3. **Python has no constant entities** (the query has no constant capture),
   so the spec's "marker constant" test device is replaced by a
   docstring marker on a function — which also proves P2-1's docstring
   backfill round-trips through the ledger.
4. **`graph_stats()["revision"]` is load-path-only:** `analyze` never stamps
   `LEDGER_REVISION` (P1 gap, noted, out of scope).

**P2-5 post-implementation notes:**
1. **Helper names** differ slightly from the spec: `textual_call_sites`
   (not `textual_occurrences`), plus `structural_call_site_lines` (the
   covered-set builder) and `push_textual_backstop` (the appender with the
   ±1 tolerance). Wired into `plan_signature_update`, `plan_rename_function`,
   and `plan_rename_class` (the spec named the two planners; the class path
   was added because it has the biggest known gap — `Old()` constructions
   resolve as External and produce no callers entry).
2. **Scanner contract:** word-boundary `name(` anywhere in a line, one
   report per line, capped at 15, definition line suppressed via the covered
   set. A non-ASCII previous byte is treated as identifier material
   (conservative: `éname(` is one token, not a call to `name`).
3. **`getattr`-style indirection stays invisible by design.** The spec's
   “dynamically constructed reference” example contains no textual `name(`,
   so no textual scan can see it. What the backstop catches is everything
   textually visible but structurally unresolvable: module-level calls, macro
   bodies, comments, strings.
4. **Tests:** 3 Rust unit tests (the spec’s fixture uses a module-level call
   as the unresolvable context — the Python analog of the macro-body case,
   since the Rust macro fixture would need a `macro_rules!`-style token body
   the extractor treats identically: opaque, unvisited) + 2 Python E2E tests
   in `tests/test_mutation_e2e.py` (dry run reports the site; apply leaves it
   on disk for the agent instead of guessing).
6. **P2-5** textual backstop (Rust) + tests → rebuild `.pyd` → Python tests. — status: DONE
