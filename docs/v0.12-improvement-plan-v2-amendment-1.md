# Amendment 1 — v0.12 improvement plan v2

> **Date:** 2026-10-06 · **Applies to:** `docs/v0.12-improvement-plan-v2.md`
> (frozen; this amendment is authoritative where it adds or narrows).
> **Trigger:** re-verification pass of the plan against the architecture
> review + decision register (see `architecture-review-amendment-1.md`).

## A1 — Decouple §0.1 from §0.6 (sequencing guard)

The plan sequences §0.6 (macrame 0.19 upgrade) *before* §0.1 (Snapshot
honesty). Correct order, wrong coupling: §0.1's lookup fix (reconstruct-backed
`find`, raise where no temporal path exists) must **not** wait on the
upgrade. Blobs extend `as_of` with old *bytes* (§3.0); honest *structure* is
independent of them.

**Rule:** if §0.6 stalls (libsql co-pin conflict, migration gap), §0.1,
§0.2, and §0.4 proceed anyway. The §0.1 "Done when" splits accordingly:
old-name-at-T is deliverable on 0.18; old-bytes-at-T arrives with §3.0.

## A2 — §0.6: use the registry version

macrame-db **0.19.0 is published on crates.io** (verified via `cargo search`;
local Macrame checkout is the same version). No git/path dependency. The
upgrade is: bump `core_indexer/Cargo.toml` to `"0.19"`, **keep the libsql pin
tracking Macrame's** (Cargo.toml:43–46 comment), confirm `Cargo.lock` shows a
single libsql, and add the mixed-store test (a 0.18 store whose cold file has
no `blobs` table must read blobs as *absent*, not error). Everything else in
§0.6 stands.

## A3 — §1.9: pin the schema and the oversize policy

Two details the plan leaves open, fixed here:

- **Key name:** the digest lives at `extra["source_blob"]` in the file
  concept. `extra` is the versioned carrier (Concept JSON v2); add the key in
  one release and treat it as required-optional (absent = pre-blob
  generation, §3.0's content-unavailable outcome). Digest shape enforced at
  the persistence boundary (64 lowercase hex — a `validate_digest`-style
  assert, tested) — as planned; the *name* is now pinned.
- **Oversize files:** a file larger than the 8 MiB blob cap (default
  `Tuning::max_blob_bytes`) is **not** an error and **not** silently
  truncated: skip the blob, flag it in the update report
  (`blob_skipped_oversize` count), keep full graph coverage for it. Pair the
  knob with the watcher's 1 MiB `max_file_size_bytes` in the `.coderadar.toml`
  docs so raising one without the other is a documented, deliberate act.

## A4 — §3.0: acceptance requires the PyO3 round-trip

"Done when: a Rust test round-trips blob_put/get" is necessary but not
sufficient — the risk lives in the **async→sync bridge** at the FFI boundary
(`tokio` runtime already present; `block_on` site belongs in `storage.rs`).
The release-gate test for §0.1/§3.0 must exercise `blob_get` **from Python
through `coderadar._core`**, asserting byte-equality of the old function body
via `Snapshot` + `read_source`-at-T. A Rust-only green test does not close
§3.0.

## A6 — P4 addition: deny-over-allow precedence

When D18 derives the default allow-list, the template docs must state in one
sentence that **deny wins over allow** where they overlap
(`/migrations/`, `/*.lock`, `/generated/` are deny-listed today). Added to the
P4 table as part of DR-27's scope.

## A7 — Release gate: one more bullet

Add to the gate list: *"DR-25 closed with commit hash, and the zero-growth
check recorded (unchanged-tree reindex wrote 0 new blob bytes)"* — making the
blob gate symmetric with the retirement gate (§0.4's retire-0 check).

## Out of scope of this amendment

No change to: P0 set and priorities, §2 skills, §3.1/§3.2 embeddings and
read-path discipline, §3.3 go/no-go gating, the diffs policy (compute, never
store), or the out-of-scope list. §3.3's frame gains one piece of evidence
from this pass: the review amendment confirms macrame 0.19's blob semantics
make bodies-at-T cheap, which *strengthens* the case for upstream traversal
once §3.0 lands — the go/no-go should weigh that.
