## Phase 0 — Correctness & write safety

These are the only findings that can damage a user's source tree or silently
degrade the graph. Everything else can wait; these cannot.

### 0.1 `rename` writes byte spans it never verified — **critical**

[`mutation/mod.rs:452`](../core_indexer/src/mutation/mod.rs#L452)

```rust
if let Some(start) = line_col_to_byte(&caller_source, call.line, call.col) {
    let end = (start + call.name.len()).min(caller_source.len());
    let span = ByteSpan { start, end };
    edits.push(MutationEdit { span, replacement: new_name, expected_hash: hash_span(&caller_source, span) });
```

The call site's byte range is reconstructed from the `(line, col)` recorded at
**index time**, then the stale-write hash is computed from the file read
**moments earlier in the same function**. The hash therefore always matches at
`apply()` time — it proves the file did not change between *plan* and *apply*,
and proves nothing about whether the graph matches disk.

When the index is stale relative to disk (the MCP server has a whole
staleness-banner subsystem, [`server.py:598`](../py_agent/src/coderadar/mcp/server.py#L598),
precisely because this is the normal state), `line_col_to_byte` resolves to
whatever now sits at that line and column, and `rename` overwrites it. The
post-write parse check ([`mutation/mod.rs:146`](../core_indexer/src/mutation/mod.rs#L146))
only catches *syntax* breakage — renaming an unrelated but syntactically valid
identifier passes verification and is committed.

**Fix:** before emitting the edit, assert
`&caller_source[start..end] == call.name.as_bytes()`. On mismatch, emit an
`UnverifiedSite` instead of an edit. Add a regression test that indexes a file,
edits it out-of-band, then plans a rename and asserts zero edits at the moved
site.

### 0.2 Renaming a class is impossible

[`mutation/mod.rs:396`](../core_indexer/src/mutation/mod.rs#L396) opens with

```rust
let fn_entity = projection.functions.get(entity_id)
    .ok_or_else(|| MutationError::EntityNotFound(entity_id.to_string()))?;
```

so the "4. Also check classes" branch at line 489 is unreachable — a class id
returns `EntityNotFound` before it is ever consulted. `coderadar_rename` on any
class fails, and no test covers it.

**Fix:** dispatch on entity kind up front; give classes their own plan path
(name span + subclass `bases` references + constructor call sites).

### 0.3 Incremental update silently drops function parameters

[`graph/projection_ops.rs:284`](../core_indexer/src/graph/projection_ops.rs#L284) —
`apply_diff_update` constructs `Function { parameters: vec![], .. }`, while the
full-index path ([`indexing.rs:188`](../core_indexer/src/graph/indexing.rs#L188))
and `insert_extracted` both use `f.parameters.clone()`.

Every function touched by `update_file` — i.e. every function in watch mode,
and every function after a mutation, since `CodeGraph.apply()` reindexes
affected files ([`__init__.py:571`](../py_agent/src/coderadar/__init__.py#L571)) —
loses its parameter list. Downstream, silently:

- `function_to_dict` renders the signature as `def foo()`
  ([`lib.rs:262`](../core_indexer/src/lib.rs#L262))
- `long-parameter-list` and `long-method` stop firing (`param_count` → 0,
  [`smells/engine.rs:147`](../core_indexer/src/smells/engine.rs#L147))
- `plan_signature_update` diffs against an empty `old_params`
- `search_entities` and the embedding pipeline embed a truncated signature

**Fix:** one-line copy. Then add a property test asserting
`analyze(f)` and `analyze(f) + update_file(f)` produce identical entities —
this class of divergence between the two ingest paths is structural and will
recur otherwise.

### 0.4 `insert_extracted` stores `name_span` as `params_span`

[`graph/projection_ops.rs:570`](../core_indexer/src/graph/projection_ops.rs#L570):
`params_span: f.name_span`. `build_fragment` and `apply_diff_update` both use
`f.params_span` correctly, so today this only affects the `index_file` path
(tests and embedded callers). But `plan_signature_update` replaces
`params_span` verbatim — any caller reaching it through `index_file` would have
the function **name** overwritten with the new parameter list.

**Fix:** correct the field. Consider collapsing the three near-identical
`ExtractedUnit → Function` constructions into one shared function; this bug and
0.3 are both copy-drift between them.

### 0.5 Mutation policy is decorative

`MutationConfig` defines `allow`, `deny`, `require_clean_git`,
`max_edits_per_plan`, `post_verify`, `backup_retention_hours`
([`graph/config.rs:101`](../core_indexer/src/graph/config.rs#L101)). Grep count
for `config.allow` / `config.deny` outside the definition: **0**. The Python
side's [`tool_router.py:211`](../py_agent/src/coderadar/mutation/tool_router.py#L211)
is:

```python
def check_policy(self, plan: Any) -> bool:
    # Verify: enabled, deny-listed paths, max_files_per_plan, max_edits_per_plan, require_clean_git
    return True
```

…and is never called by anything.

Meanwhile [`lib.rs:726`](../core_indexer/src/lib.rs#L726) `apply_mutation`
accepts an arbitrary JSON plan — file path, byte span, replacement, and an
`expected_hash` that **defaults to empty**, which
[`mutation/mod.rs:619`](../core_indexer/src/mutation/mod.rs#L619) treats as
"skip the stale check". An MCP-driven agent can write any span of any file,
including outside the project root, with no policy gate and no staleness guard.

**Fix:** enforce `deny`/`allow` against the canonicalised target path inside
`MutationEngine::apply` (Rust side — the trust boundary is the FFI, not the
Python caller), enforce `max_edits_per_plan`, and reject plans whose edits carry
an empty `expected_hash` unless the tool is `create_entity`. Wire
`require_clean_git` to the existing `git_worktree_clean` binding. Delete
`check_policy` rather than leaving a stub that reads as implemented.

### 0.6 Reported outcomes that were never checked

Three places report success they did not verify:

- [`lib.rs:648`](../core_indexer/src/lib.rs#L648) — `update_file` hardcodes
  `parse_quality: "clean"`, `parse_errors: 0`, `elapsed_ms: 0.0`. The Python
  `UpdateReport` and the MCP `_update_file` failure branch
  ([`server.py:1683`](../py_agent/src/coderadar/mcp/server.py#L1683)) both key
  off `parse_quality`, so the failure branch is dead.
- `ParseQuality::Clean` is hardcoded at **every** entity construction site
  (7 occurrences across `indexing.rs` / `projection_ops.rs`); `content_hash: 0`
  likewise. Tree-sitter `ERROR` nodes are never recorded, so the
  `plan_body_replacement` warning at
  [`mutation/mod.rs:249`](../core_indexer/src/mutation/mod.rs#L249) can never
  fire.
- [`__init__.py:593`](../py_agent/src/coderadar/__init__.py#L593) —
  `CodeGraph.apply()` returns `status="Applied"` with
  `files_written=plan.affected_files` whenever the Rust call succeeded, throwing
  away the real `files_written` from the result dict, and returns the same
  "Applied" on `ImportError`.

**Fix:** thread real values through. `has_error()` is already available at the
parse site — record it once per file and propagate.

### 0.7 The four primary MCP tools crash before first index

Reproduced in a fresh interpreter:

```
explore RAISED RuntimeError No graph loaded — run coderadar init first
search  RAISED RuntimeError No graph loaded — run coderadar init first
```

`_explore` / `_search` / `_node_detail` / `_affected` guard with
`except ImportError` ([`server.py:836`](../py_agent/src/coderadar/mcp/server.py#L836)),
but `with_graph` raises `PyRuntimeError`. The intended friendly message —
*"No index available. Run `coderadar init` in the project root first"* — is
reachable only when a graph is loaded *and* empty, which never happens.
`_update_file` is the one function that catches `RuntimeError`.

The existing tests pass `graph=None` and assert only
`isinstance(result, str) and len(result) > 0`
([`test_mcp.py:898`](../tests/test_mcp.py#L898)) — an assertion that a
stack-trace string would also satisfy.

**Fix:** a `@requires_index` decorator replacing the ~15 copies of this guard,
catching `(ImportError, RuntimeError)`. Tighten the uninitialised-state tests to
assert on message content.

## Phase 1 — Make the temporal claim true

The README's headline differentiator is *"query the graph as it existed at any
point in time."* Three defects mean the ledger records only additions.

### 1.1 Nothing is ever retired

`retired: false` appears once, in
[`storage.rs:211`](../core_indexer/src/storage.rs#L211); `retired: true` appears
nowhere. No `valid_to` is ever closed on a concept, and no edge is ever
invalidated. A deleted function, a renamed class, a removed import — all remain
"currently true" in the bitemporal ledger forever. `codegraph_as_of` for any
past timestamp returns a superset that grows monotonically and never shrinks.

**Fix:** `remove_file_entities` and `apply_diff_update` already compute the
removed-id set. Close those concepts (`valid_to = now`, `retired = true`) and
retract their edges in the same transaction.

### 1.2 A one-file edit rewrites the entire edge set

[`graph/projection_ops.rs:452`](../core_indexer/src/graph/projection_ops.rs#L452) —
`update_file` calls `persist_edges(&projection)`, which iterates *all* of
`callees_by_caller`, `importers`, every class's `resolved_bases`, and
`overrides_base` for the whole graph and re-asserts every edge with a fresh
`valid_from` ([`persistence.rs:24`](../core_indexer/src/graph/persistence.rs#L24)).

On a 558-file project that is tens of thousands of edge assertions per
keystroke-debounced save. The ledger grows without bound, and every duplicate
assertion is also a new "version" that `as_of` must reconstruct through.

**Fix:** scope `persist_edges` to the changed file's edges, mirroring the
existing `resolve_calls_scoped(projection, Some(file_path))` split. This is also
the largest single win available in watch-mode latency.

### 1.3 File deletions never reach the graph

`FileChangeKind::Delete` is declared
([`fs/watcher.rs:32`](../core_indexer/src/fs/watcher.rs#L32)) and never
constructed — `notify-debouncer-mini`'s `DebouncedEventKind` only yields
`Any` / `AnyContinuous`, both mapped to `Any` / `Modify`
([`watcher.rs:108`](../core_indexer/src/fs/watcher.rs#L108)). The Python loop
then dispatches on `"Modify" | "Any" | "AnyContinuous" | "Create"`
([`__init__.py:832`](../py_agent/src/coderadar/__init__.py#L832)), so both the
`Delete` and `Create` branches are dead.

Delete a file in watch mode and its entities live on in the projection, in the
ledger, and in every query result.

**Fix:** stat the path on event; absent ⇒ `Delete` ⇒ `remove_file_entities` +
retirement (1.1). Same-shaped test as `test_e2e.py:366`.

### 1.4 `--debounce` does nothing

`coderadar watch --debounce 50` ([`cli.py:626`](../py_agent/src/coderadar/cli.py#L626))
→ `graph.watch(paths, debounce_ms=debounce)` → stored as `self._debounce_ms`
and never read. `start_watcher(paths)`
([`lib.rs:1400`](../core_indexer/src/lib.rs#L1400)) builds
`WatcherConfig { watch_paths, ..Default::default() }`, so debounce is always
100 ms. `max_file_size_bytes` is likewise defined and never enforced.

**Fix:** add the parameter to the binding, or drop the flag. Don't ship both.

## Phase 2 — Scaling

`performance-roadmap.md` covers parse and resolve throughput. These are
different: algorithmic shapes that are fine at 84 files and quadratic at 5,000.

### 2.1 Whole-projection clone per single-entity write — **highest impact**

Four APIs clone the entire `ProjectedGraph` to modify one field:

| Call site | Called once per |
|---|---|
| [`embeddings.rs:15`](../core_indexer/src/graph/embeddings.rs#L15) `set_embedding` | **entity** |
| [`embeddings.rs:82`](../core_indexer/src/graph/embeddings.rs#L82) `set_module_star_exports` | **module with `__all__`** |
| [`persistence.rs:122`](../core_indexer/src/graph/persistence.rs#L122) `register_synthetic_edge` | **framework edge** |
| [`indexing.rs:304`](../core_indexer/src/graph/indexing.rs#L304) `index_file_inner` | **file** |

`compute_embeddings` ([`__init__.py:385`](../py_agent/src/coderadar/__init__.py#L385))
loops `set_embedding` over every entity, so embedding a 10k-entity project
performs 10,000 full-projection clones — O(N²) Arc clones and hashmap rebuilds.
`analyze()` does the same over every file with `__all__`
([`__init__.py:712`](../py_agent/src/coderadar/__init__.py#L712)), and the 13
framework resolvers do it per route edge.

**Fix:** bulk variants (`set_embeddings_bulk(Vec<(id, vec, hash)>)`,
`register_synthetic_edges_bulk`, `set_module_star_exports_bulk`) that clone
once and apply N mutations. Cheap to implement, and it removes the dominant
cost of `coderadar init --with-embeddings`.

### 2.2 Two O(F²) scans inside resolution

[`graph/resolve_calls.rs:216`](../core_indexer/src/graph/resolve_calls.rs#L216) —
`sibling_funcs` is built by scanning **all** functions filtered by
`parent_module`, once per module: O(modules × functions).

[`graph/resolve_calls.rs:46`](../core_indexer/src/graph/resolve_calls.rs#L46) —
`mro_methods` scans **all** functions once per MRO node, once per function:
O(functions² × mro_depth). This runs inside the parallel worker, so each of the
4 threads pays it independently.

**Fix:** build `parent_module → [function]` and `parent_class → [function]`
indexes once per resolve pass and pass them down. Both are single-pass groupings
over `projection.functions`.

### 2.3 Same shape in the smell engine

[`smells/engine.rs:166`](../core_indexer/src/smells/engine.rs#L166) and
[`:193`](../core_indexer/src/smells/engine.rs#L193) — `metrics_for_class` and
`coupling_between_objects` each scan all functions per class. `codegraph_get_smells`
is O(classes × functions) with a factor of two.

**Fix:** the same `parent_class → [function]` index from 2.2, computed once in
`SmellEngine::run`.

### 2.4 The query executor materialises before it filters

[`query/exec.rs:96-188`](../core_indexer/src/query/exec.rs#L96) builds a full
`QueryRow` — including cloned `callers` and `callees` id lists — for **every**
entity, then evaluates the `WHERE` clause at line 190 and discards the row.
`functions where name = "x"` allocates the whole graph.

**Fix:** evaluate the predicate against lazily-resolved fields; materialise only
survivors. Push `limit` down when there is no `ORDER BY`.

### 2.5 Dead allocation on every resolve pass

[`graph/resolve_calls.rs:135`](../core_indexer/src/graph/resolve_calls.rs#L135) —
`_definitions_pool` clones id, name, and module for every function in the graph
and is never used (underscore-prefixed). Delete.

## Phase 3 — Configuration that isn't wired

`.coderadar.toml` is 100+ documented knobs across 13 sections.
`load_config` ([`config.py:205`](../py_agent/src/coderadar/config.py#L205)) is
called from exactly one place: `tests/test_python_layer.py:62`. Nothing in the
CLI, the MCP server, or the Rust core reads it — every consumer constructs
`GraphConfig::default()` ([`lib.rs:359`](../core_indexer/src/lib.rs#L359),
`:664`, `:681`, `:699`, `:717`, `:768`).

Consequences worth naming:

- `.coderadar.toml`'s `[database] path = ".harness/semantic.db"` contradicts the
  actual store at `.coderadar/store/coderadar.db`
  ([`lib.rs:363`](../core_indexer/src/lib.rs#L363)), and carries `hnsw_*` keys
  with no model field at all.
- `load_harness_config` reads `.harness/config.toml`, deleted in `105762e`.
- The embedding model is specified three times with two different values:
  `.coderadar.toml` and `EmbeddingDedup.__init__` say
  `jinaai/jina-code-embeddings-0.5b` (896-dim);
  `CodeGraph.compute_embeddings` passes `BAAI/bge-small-en-v1.5` (384-dim)
  ([`__init__.py:337`](../py_agent/src/coderadar/__init__.py#L337)).

**Fix (pick one and commit to it):** either load `.coderadar.toml` at CLI/server
startup and pass a `GraphConfig` through the FFI, or cut the file and the
pydantic models down to what is actually read. The current state — a fully
documented config surface with zero effect — is the worst of both.

### 3.1 Two embedding hazards worth fixing regardless

- [`dedup.py:83`](../py_agent/src/coderadar/embedding/dedup.py#L83) — when
  `fastembed` is missing, `_model_embed` returns **zero vectors**, which
  `set_embedding` stores with a valid content hash. `has_embedding` becomes
  true, the dedup cache treats them as fresh, and semantic search is silently
  and permanently poisoned. Raise instead.
- `search_entities` ([`lib.rs:821`](../core_indexer/src/lib.rs#L821)) only
  handles `function`, `class`, `module`. `compute_embeddings` requests
  `import`, `constant`, and `type_alias` too — those return empty, so the three
  entity kinds the `codegraph_search_similar` description promises are never
  embedded.

## Phase 5 — Engineering hygiene

### 5.1 CI gaps

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml):

- Runs `tests/test_e2e.py tests/test_mcp.py tests/test_framework_resolvers.py`
  — **250 of 343** Python tests. Not run: `test_python_layer.py` (64),
  `test_semantic_engine.py` (13), `test_v1_gaps.py` (7), `test_smells.py` (5),
  `test_smells_golden.py` (4). `pyproject.toml` already sets
  `testpaths = ["tests"]`; CI narrows it deliberately.
- **Ubuntu only.** The codebase is dense with Windows path handling
  (`normalize_path_str`, `.\`-prefixed entity ids, the three-candidate path
  guessing in `clear_embeddings_for_file`) and the primary dev environment is
  Windows. Path-separator bugs cannot be caught today.
- No `cargo clippy`, no `cargo fmt --check`, no `ruff`, no `mypy` — the last two
  are declared dev dependencies with a configured `[tool.ruff]` section.

**Fix:** run the whole suite; add a `windows-latest` matrix leg; add
clippy/ruff as non-blocking first, then blocking.

### 5.2 Compiler warnings

64 from `cargo check --all-targets`, of which these are substantive:

- [`types.rs:209`](../core_indexer/src/types.rs#L209) — `"sh" | "bash" | "zsh" => Language::Shell`
  is unreachable; line 197 already maps `"sh" | "bash"` to `Language::Bash`.
  `.sh` and `.zsh` therefore resolve to different `Language` variants and
  potentially different grammars.
- [`types.rs:452`](../core_indexer/src/types.rs#L452) — duplicate `"Int"` /
  `"Double"` arms in the builtin-type stoplist (harmless, but noise).
- [`update/diff.rs:61`](../core_indexer/src/update/diff.rs#L61) — private type
  `MatchKey` leaks through a `pub` method.
- [`single_pass.rs:26`](../core_indexer/src/extract/single_pass.rs#L26) — four
  never-read fields on `Emitted`.
- 6 deprecated PyO3 calls (`into_py`, migration guide for 0.23) plus ~15
  `unsafe { Python::assume_gil_acquired() }` sites in `lib.rs` that should take
  a `py: Python<'_>` parameter instead. These will break on the next PyO3 bump.
- 19 unused imports, 17 needless `mut`, and a stray `;;` at
  [`lib.rs:59`](../core_indexer/src/lib.rs#L59).

`cargo fix` handles 33 of them automatically.

### 5.3 Small correctness nits

- [`lib.rs:128`](../core_indexer/src/lib.rs#L128) — `PyCodeGraph::new` takes
  `GLOBAL_GRAPH.write()` into an unused `guard` and comments "Seed the global
  graph from this instance"; it seeds nothing and holds a write lock for the
  duration of the constructor.
- `class_to_dict` and `constant_to_dict` set `embedding_hash` twice
  ([`lib.rs:198`](../core_indexer/src/lib.rs#L198), `:296`).
- `function_to_dict` sets `has_embedding` **only when non-empty**
  ([`lib.rs:243`](../core_indexer/src/lib.rs#L243)); every other `*_to_dict`
  always sets it, so Python code reading `entity["has_embedding"]` raises
  `KeyError` for un-embedded functions.
- `traverse` calls `entity_ref_to_dict(...).is_none()` purely as an existence
  check ([`lib.rs:1057`](../core_indexer/src/lib.rs#L1057)), building and
  discarding a full dict.
- [`analyze`](../core_indexer/src/lib.rs#L487) swallows both per-file
  extraction errors and worker-thread panics with `Err(_) => {}`. A panicking
  thread silently drops a whole bucket of files from the index.
- `resolve_calls_scoped` scopes by `f.parent_module.contains(fp)`
  ([`resolve_calls.rs:158`](../core_indexer/src/graph/resolve_calls.rs#L158)) —
  substring matching, so `a.py` also scopes `xa.py` and `a.pyi`.

### 5.4 `diff_preview` is not a diff

[`mutation/mod.rs:241`](../core_indexer/src/mutation/mod.rs#L241) produces
`"replace 412 bytes at 1830..2242 in ./src/x.py::module"`. The MCP tool
description promises *"returns a diff preview for review"*
([`server.py:429`](../py_agent/src/coderadar/mcp/server.py#L429)) and
`_format_mutation_plan` renders it inside a ```` ```diff ```` fence. An agent
following the documented review-then-apply workflow has nothing to review.

**Fix:** render a real unified diff from `original[span]` → `replacement`.
`plan.unverified_sites` is also missing from `plan_to_dict`
([`lib.rs:782`](../core_indexer/src/lib.rs#L782)), so the "N call sites could

## Phase 6 — MCP initialization, path resolution & lifecycle

Incorporates the *MCP Initialization & Path Resolution* proposal (2026-07-11),
which ports `codegraph-main`'s `src/mcp/{session,engine,index,daemon-paths}.ts`
and `src/directory.ts` patterns. The six observed failures it names (F1–F6) are
real and reproduce against this code. This section keeps its shape and priorities
and corrects it where verification disagreed.

### 6.0 Verification of the incoming proposal

**Confirmed as written:**

- `mcp serve` blocks the handshake on a full synchronous `analyze()`
  ([`cli.py:546`](../py_agent/src/coderadar/cli.py#L546)) — F2 is real.
- Zero references to `rootUri` / `workspaceFolders` / `roots` anywhere in
  `mcp/` (grep across all 7 modules: 0 hits).
- 18 `@mcp.tool()` handlers, every one closing over a single `graph` captured
  at `create_server(graph)` — F6's premise holds.
- No lifecycle hygiene of any kind: `serve()` is
  `create_server(graph); server.run(transport="stdio")`. No PPID watchdog, no
  handshake timeout, no stdin teardown — F5 is real.
- The Rust core exposes no multi-project open/close; `analyze` swaps a single
  `GLOBAL_GRAPH` ([`lib.rs:560`](../core_indexer/src/lib.rs#L560)).
- `.coderadar/config.toml` is written by `coderadar init`
  ([`cli.py:112`](../py_agent/src/coderadar/cli.py#L112)) and is a sound
  walk-up marker.

**Corrections — six items:**

#### C1. `rootUri` and `workspaceFolders` do not exist in MCP

They are LSP concepts. The installed SDK's `InitializeRequestParams` has exactly
four fields: `meta`, `protocol_version`, `capabilities`, `client_info`. Even if
a host sent `rootUri`, pydantic drops unknown fields before CodeRadar could read
it. **Rungs 1 and 2 of the proposed precedence ladder are unimplementable.**

The ladder collapses to: **`roots/list` → `--path` flag → cwd** — which is not a
downgrade, because of C2.

#### C2. Task 0's spike is already answered, and favourably

`mcp.server.session.ServerSession` exposes `list_roots()`,
`check_client_capability()`, `client_capabilities`, and `client_params`.
Server→client `roots/list` is fully supported, and `mcp.types` carries
`ListRootsRequest`, `ListRootsResult`, `Root`, `RootsCapability`. The roots
dance is therefore the **primary** client signal, not a fallback.

One structural constraint: `MCPServer` has no `initialize` hook (its public
surface is `tool`/`resource`/`prompt`/`run`/…). Resolution must happen either on
first tool call — tools can request a `Context` parameter, which reaches the
session — or by dropping to `mcp.server.lowlevel.Server.add_request_handler`.
Prefer the former; it is also where the lazy-retry logic of Phase 3 lives.

**Task 0 drops from a ½-day spike to a ~1-hour design decision.**

#### C3. Phase 1 as written makes the problem worse — Rust prerequisite required

`analyze()` never releases the GIL. It is declared `fn analyze(root: &str)` with
no `Python<'_>` parameter and no `allow_threads`, and reaches for
`Python::assume_gil_acquired()` only at the end
([`lib.rs:354-568`](../core_indexer/src/lib.rs#L354)).

Measured on this project (84 source files) with a 10 ms ticker thread:

```
analyze() wall time: 3.29s
ticker samples: 21, largest stall: 3.30s   → GIL held throughout
```

`asyncio.to_thread(analyze, candidate)` would therefore freeze the entire event
loop for the duration of indexing. The server would answer `initialize` in
<100 ms and then go **completely unresponsive** for minutes on a large repo —
strictly worse than today's honest slow start, because the client sees a hung
server rather than a starting one.

**Prerequisite (blocks Phase 1):** restructure `analyze` to take
`py: Python<'_>` and wrap the walk / parse / resolve / persist phases in
`py.allow_threads(|| …)`, re-acquiring only to build the return dict. ~½ day of
Rust work. The same treatment is owed to `update_file`, which has the identical
shape. (`traverse`, `traverse_unresolved`, and `get_smells` already do this
correctly — copy their pattern.)

#### C4. The real root cause of F1 is deeper: the server assumes `cwd == project root`

"No client-side path signals honored" is only half of it. **`--path` itself is
only half-wired**, because every read helper resolves against the process cwd:

| Site | Coupling |
|---|---|
| [`server.py:1742`](../py_agent/src/coderadar/mcp/server.py#L1742) `_read_source` | `open(file_path)` — graph-relative path, cwd-resolved |
| [`server.py:617`](../py_agent/src/coderadar/mcp/server.py#L617) `_get_stale_files` | `os.path.getmtime(fp)` — same |
| [`server.py:1544`](../py_agent/src/coderadar/mcp/server.py#L1544) `_canonical_file_path` | `os.path.relpath(fp, os.getcwd())` |
| [`server.py:1783`](../py_agent/src/coderadar/mcp/server.py#L1783) `_canonical_entity_id` | probes `os.getcwd()` across 4+ candidate spellings |
| [`server.py:1643`](../py_agent/src/coderadar/mcp/server.py#L1643) `_reindex` | hardcodes `analyze('.')`, with a comment stating that an absolute root would change entity-id prefixes |

Entity ids are prefixed with the path `analyze()` walked. Serving
`--path /other/project` produces ids prefixed `/other/project/…` while every
helper above probes cwd — so lookups miss, `_read_source` opens nothing, and the
agent sees an empty or wrong-looking project. That is the likely mechanism
behind F1, and no amount of client-signal plumbing fixes it.

**Phase 2 must additionally** either `os.chdir(resolved_root)` immediately after
resolution (cheap, correct for a single-project server, and makes `analyze('.')`
in `_reindex` right by construction) or make entity ids root-relative in the
core (better, larger). Pick one before writing the ladder. The ad-hoc
multi-spelling probing in `_canonical_entity_id` should then be deleted, not
extended.

#### C5. `analyze()` creates the marker it is supposed to discover — wrong guesses become sticky

[`lib.rs:363`](../core_indexer/src/lib.rs#L363) unconditionally
`create_dir_all(<root>/.coderadar/store)` before indexing. Verified:
`analyze('py_agent')` on a directory that was never `init`-ed created
`py_agent/.coderadar/store/coderadar.db` (removed afterwards).

So if the resolver guesses wrong once, `analyze()` plants a `.coderadar/` there,
and the next walk-up **finds that marker and re-confirms the wrong root**. F1
becomes self-reinforcing.

**Fix, and it belongs in Phase 2, not later:** gate on marker existence *before*
calling `analyze()`, and make store creation conditional on an explicit
`create: bool` (set only by `coderadar init`). Without this, walk-up discovery
is actively dangerous.

#### C6. The staleness banner is ported but inert — the gap table's "✅ done" is wrong

`_get_stale_files` reads `stats.get("epoch", 0)`
([`server.py:612`](../py_agent/src/coderadar/mcp/server.py#L612)), but
`graph_stats()` never sets an `epoch` key — verified keys are exactly
`call_edges, classes, constants, file_count, functions, imports, modules,
type_aliases` ([`lib.rs:1175`](../core_indexer/src/lib.rs#L1175)). `index_epoch`
is therefore always `0`, and the guard `if index_epoch > 0` never passes.

Confirmed empirically: `os.utime('README.md')` followed by
`_get_stale_files(['README.md'])` returns `[]`.

**Every staleness banner in the server is dead code.** This compounds §0.1 —
`rename` writes byte spans derived from a possibly-stale index, and the one
mechanism that would have warned the agent never fires. Fix by exposing an index
timestamp from the core (`graph_stats()["indexed_at"]`), set at
`commit_projection`.

#### Answered open question: `analyze()` re-entrancy (proposal §8.2)

Yes, and cleanly. Measured:

| Call | Result |
|---|---|
| `analyze('.')` | 148 modules, 1528 functions, 3.2 s |
| `analyze('.')` again | 148 modules, 1528 functions — no doubling |
| `analyze('py_agent')` | 45 modules, 418 functions — full replacement, not a merge |

Phase 3's per-tool-call re-walk needs no core-level reset. Note that each call
opens a fresh `CodeGraphStore` and drops the previous one along with its tokio
`Runtime`; worth a look under a load test, not a blocker.

## Sequencing

| Phase | Content | Effort | Risk if deferred |
|---|---|---|---|
| **0** | Write-path correctness (0.1–0.7) | ~2 days | Silent source corruption |
| **1** | Temporal truth (1.1–1.4) | ~3 days | The headline feature is wrong |
| **2** | Scaling (2.1–2.5) | ~2 days | Blocks projects >1k files |
| **5.2/5.3** | Warnings + nits | ~0.5 day | Blocks the next PyO3 bump |
| **5.1** | CI: full suite + Windows leg | ~0.5 day | Everything above regresses |
| **3** | Config: wire or cut | ~2 days | Growing doc/behaviour gap |
| **4** | Dead-code retirement | ~1 day | Edits to dead files silently no-op |
| **5.4** | Real diffs in mutation plans | ~1 day | Agent workflow is unreviewable |
| **6** | MCP init / paths / lifecycle | ~8.5 days | F1–F6 recur; wrong-project resolution is self-reinforcing |

Suggested order: **5.1 first** (so the rest is guarded), then 0 → 2.1 → 1 → 4 →
3 → 5.2/5.3 → 5.4. Phase 2.1 is pulled forward because it is a few hours of
work for the largest single measurable win.

**Phase 6 runs as a parallel track** — it touches `mcp/` and `cli.py`, which
Phases 0–5 barely overlap. Two exceptions to coordinate:

- **6/C3 ↔ 2.1** — both restructure GIL handling and hot Rust paths; do 2.1
  first, then C3 inherits a cheaper `analyze`.
- **6/C6 ↔ 0.1** — the staleness fix is what makes `rename`'s span verification
  legible to the agent. Land 0.1 regardless; C6 turns a silent guard into a
  visible warning.

If Phase 6 is the priority (it fixes user-visible failures, where Phases 0–5 fix
latent ones), the minimum safe prefix from this plan is **5.1 → 0.1 → 0.5 → 6**.

### Cross-cutting test debt

Three gaps make the above hard to hold onto:

1. **No end-to-end mutation test.** `mutation::tests` exercises `apply()` on
   synthetic plans; nothing drives plan → apply → reindex → assert-file-contents
   through the Python or MCP layer. 0.1–0.4 all live in that gap.
2. **Assertions that cannot fail.** ~15 MCP tests assert only
   `isinstance(result, str) and len(result) > 0`.
3. **No parity test between the two ingest paths.** `analyze` (via
   `build_fragment`) and `update_file` (via `apply_diff_update`) construct
   entities independently; 0.3 is the second such divergence found.
