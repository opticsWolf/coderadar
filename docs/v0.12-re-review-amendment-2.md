## Re-review outcome

The tracked source tree has not changed since the prior architecture review:
`git status` shows no tracked-code diff, the version is still **0.11.0** in
`pyproject.toml` and workspace `Cargo.toml`, and the CodeRadar dependency is
still `macrame-db = "0.18"` (`Cargo.lock`: 0.18.0). No v0.12 implementation
or version-bump commit has landed. Accordingly, the earlier architecture
findings D9–D20 remain current; this review adds no claim that they have been
fixed.

The most important new outcome is documentary: Amendment 1's new DRs are
still proposals, but the plan amendment now cites them as if they were active
register rows. The plan also has several implementation contracts that are
not yet specific enough to make the proposed blob history safe and testable.

## New amendment list

### A8 — Reconcile proposed DR rows with the actual decision register

The graph-stored decision register still ends at **DR-24**, followed by
un-numbered proposals **P-A/P-B/P-C**. Amendment 1 §4 proposes DR-25 through
DR-29, but explicitly leaves them for a later register update. In contrast,
plan Amendment 1 §A5 calls the mappings concrete and §A7 gates on DR-25. These
statements are not yet equivalent: an amendment proposal is not a row in the
register.

**Clarification (supersedes the operative reading of Amendment 1 §A5/A7):**
DR-25..DR-29 are provisional identifiers until an amendment to the decision
register actually adds them. Before implementation begins, either add those
rows to the register or keep plan references explicitly marked *proposed*.
Do not report the release gate as satisfied by a row that does not exist.

### A9 — Correct the blob DR cross-reference and pin the actual `extra` path

Two related inconsistencies need correction before coding:

1. Plan §1.9 currently cites **DR-11**, whose register row is the in-process
   **vector** decision. Blob-backed source history is not the vector decision;
   it belongs under proposed **DR-25**. §0.6 may cite DR-3 as the historical
   Macrame migration lineage, but the blob design decision should be DR-25.
2. The plan amendment says `extra["source_blob"]` and describes `extra` as
   "Concept JSON v2". In current `core_indexer/src/storage.rs:772–780`,
   CodeRadar emits `extra` as
   `{"coderadar":{"format":1,"kind":...,"file_path":...,"content_hash":...}}`.
   The content metadata has its own `meta_version`; that is distinct from
   `extra.coderadar.format`.

**Amendment:** use the CodeRadar namespace, e.g.
`extra.coderadar.source_blob`, on the file's **module concept** only. State
whether this additive field keeps `coderadar.format = 1` or advances that
format; do not conflate it with the content `meta_version`. Add serialization
and ledger-reconstruction tests for both legacy extra (no digest) and new
extra (lowercase 64-hex digest). The archive's reference scan must see the
serialized nested digest.

### A10 — Add a source-data security decision before enabling blobs by default

The blob plan persists entire source files as raw BLOB values, then retains
some bytes in the cold archive and requires backups to include both files.
This is a material increase in the store's sensitivity: current CodeRadar
persists metadata and hashes, not full source bodies. The built-in
`DEFAULT_EXCLUDES` do not name `.env`/secret patterns, and the secret scanner's
contract is to redact **findings/output**; it does not redact the source bytes
that a blob would store. Macrame's `blob_put` stores the input bytes as given.

**Amendment:** before the default write path lands, record the policy decision
in proposed DR-30: is source-blob storage opt-in, or default-on with an
explicit user notice and documented at-rest protections? In either case, the
policy must cover the hot database, cold archive, exported/copied backups,
access permissions, retention, and deletion/erasure. Do not treat output
redaction or `.gitignore` as at-rest protection. Add a fixture containing a
secret-shaped sentinel to verify the chosen storage and reporting behavior.

### A11 — Make the historical-source API genuinely byte-faithful

The current `ops.read_source` (`ops.py:485`) opens **today's disk file** as
UTF-8 with `errors="replace"`, slices by line numbers, and prefixes every
line with a line number. That is a display string, not original source bytes.
The plan and Amendment 1 §A4 currently ask for byte equality through
`Snapshot` plus `read_source`, which the existing function cannot establish.

**Amendment:** separate the contracts:

- a raw-byte path fetches the digest from the historical module concept,
  verifies/uses the stored byte spans, and returns the exact original byte
  range (or the full original file bytes); and
- a display path may decode/format those bytes, with the existing line-number
  prefix clearly treated as presentation.

Pin an explicit public/internal API name and error outcomes for missing
historical body, invalid digest, and invalid/out-of-range span. Test exact raw
bytes for CRLF and non-ASCII source, and separately test the formatted text.
This is part of proposed DR-25's acceptance, not evidence that the existing
`read_source` already meets it.

### A12 — Specify blob oversize, partial-write, and retry behavior end-to-end

Macrame 0.19 `Database::blob_put` returns `BlobTooLarge` above
`Tuning::max_blob_bytes`; it does not silently skip or emit a CodeRadar
report. Amendment 1 §A3 proposes "skip + `blob_skipped_oversize` count", but
CodeRadar's current `UpdateReport` (`py_agent/src/coderadar/__init__.py:104`)
has no such field, and the Rust/Python/CLI/MCP report serializers would all
need to carry it. Also, blob insertion and the concept assertion are separate
operations, not one transaction.

**Amendment:** define one consistent result for `analyze`, `reindex`,
`update_file`, and watcher ingestion when a source file exceeds the blob cap:
keep the graph update or reject it, mark historical body as unavailable, and
surface a typed count/status through each relevant report surface. The
watcher's 1 MiB cap does not constrain full walks/reindex, so test both paths.
Keep the safe ordering (put bytes before asserting their digest); inject a
failure between put and assertion and prove retry is idempotent and never
leaves a live digest reference to absent bytes. Orphan blobs are acceptable
only if their archive/retention fate is documented and bounded.

### A13 — Turn the backup requirement into a coherent-pair restore test

Plan §3.4 correctly says a backup must include hot and cold files, because a
snapshot carries digests rather than bodies. It does not yet say how to obtain
a mutually consistent pair while archive activity may be changing them.

**Amendment:** specify a quiesced/atomic backup procedure (including snapshots
and any required checkpoint/close step), then test restore from that backup:
for every retained source digest referenced by reconstructed ledger history,
`blob_get` succeeds and yields the expected bytes. Include a cold archive
created before 0.19 (no `blobs` table) and a newer archive containing blobs.
A pair of files copied at unrelated instants is not a passing backup.

### A14 — Strengthen the clone determinism acceptance to a total order

Plan §0.2's `(file, start_line)` candidate sort is not a total order: entities
can tie on those fields. Current `detect_clones` (`clones/mod.rs:193–194,
248–267, 359–412`) traverses hash maps for functions, raw/normalized buckets,
and clusters; `LshIndex::candidate_pairs` (`lsh_index.rs:46–62`) traverses
`HashMap::values()` and a `HashSet`; `build_group` preserves member order; the
final group sort compares only instance count and similarity. The FFI applies
`max_groups` after this sort (`lib.rs:3096`), so equal-ranked groups can still
change which results are returned.

**Amendment:** make every observable boundary deterministic before the
`max_groups` cut: fingerprint order by a total key such as
`(file, span.start, span.end, entity_id)`; canonicalize member/instance order;
order bucket keys and candidate pairs; and sort final groups by a total key
including clone type and canonical member IDs after size/similarity. Test
multiple insertion/hash seeds, exact ties, and `max_groups` truncation; compare
serialized JSON bytes, not only group counts.

### A15 — Align sequencing with Amendment 1's §0.1/§0.6 decoupling; fix the typo

Amendment 1 §A1 says structural honesty (§0.1) proceeds if the Macrame upgrade
stalls, and old bytes wait for §3.0. The plan's sequencing table still puts
§0.1 and §1.9 together **after** §0.6 (step 3). The exception is described
but not represented in the schedule.

**Amendment:** split §0.1 into (a) reconstruct-backed, recorded-time
structural lookup that can land independently and (b) historical-byte reads
that wait for §0.6 + §1.9 + §3.0. Do not make the whole §0.1 item green until
both contracts pass. Update step 3/5 and the release gate accordingly. Also
fix the malformed phrase in §1.9 step 4, `"-doS the other"`, to the intended
"raising one cap does not silently raise the other" wording.

### A16 — Pin `as_of` to a temporal axis and normalize timestamps at the boundary

For historical code search, the relevant question is normally **what CodeRadar
had recorded/believed at T**, i.e. transaction/recorded time. Macrame 0.19's
`reconstruct(ts)` folds `transaction_log` rows where `recorded_at <= ts`; it is
not the same question as valid-time `as_of_valid`. Meanwhile CodeRadar's
current `ops.as_of` validates with `datetime.fromisoformat`, which accepts
naive and offset timestamps, while Macrame 0.19's `timestamp::normalize`
requires fixed-width UTC `...Z` (and rejects offsets/naive values).

**Amendment:** say explicitly that the code-history surface means recorded
(time CodeRadar indexed/learned the code), or document why it means something
else. Normalize accepted inputs to the Macrame canonical UTC format or reject
noncanonical inputs as `InvalidRequest` before entering the engine. Test
canonical UTC, seconds-only UTC if retained, timezone offset, naive timestamp,
retroactive correction, and an instant before recorded history. Surface
`predates_recorded_history` distinctly from a missing entity/body.

The proposed DR-25..DR-30 rows above are not yet registered and have no

process rule. Version remains 0.11.0 until a feature lands; then apply the
