## The theme

v0.7 was about **honesty**: it removed everything that reported success it had
not earned — fabricated diagrams, hardcoded `parse_quality: "clean"`, exit code
0 on failure, a `mutations` command backed by nothing, ~100 config knobs with
no effect, ~4,300 lines of dead code, and guidance strings naming tools that do
not exist.

That work is done, and it left the project in a specific state: **honest but
slow, and honest but incomplete.** Three of the four highest-value items below
exist because v0.7 replaced a lie with a loud refusal and stopped there. A
refusal is the right interim state; it is not the destination.

v0.8 is about **making the honest answers useful**:

| v0.7 shipped | v0.8 owes |
|---|---|
| `explore()` refuses non-call edge kinds instead of faking them | `explore()` walks all four kinds through the Rust binding |
| `_ensure_graph()` re-indexes so read commands can answer at all | cold start from the ledger, so answering is cheap |
| `export_snapshot`/`load_snapshot` raise loudly | they work |
| `as_of` rejects upstream traversal | it doesn't need to, or the docs say why permanently |

## Phase 1 — Cold start (the load-bearing gap)

*Goal: stop paying a full re-analysis for every process that wants to read the
graph. This is Phase 3B, deferred through v0.6 and v1-readiness, and §1.2 of
`open-items.md` promoted it from "nice" to "load-bearing".*

The measured cost is not theoretical: `v1-readiness-plan.md` §1.4 recorded a
cold `analyze()` at **~46 s** on a 605-file repo. Since `b140cbf`, every
`coderadar query`, `stats`, `callers`, `traverse`, and `visualize` invocation
pays it, because `_ensure_graph` is what makes them able to answer at all.

Everything Phase 1 needs already exists. The Macrame ledger is written on every
index (`persist_entities`, `persist_edges`), edges for all four kinds have been
persisted since `c0bc99e`/`445b0c4`, timestamps are correct since v1 §2.5, and
`CodeGraphStore::reconstruct(ts) -> MaterializedState`
([`storage.rs:160`](../core_indexer/src/storage.rs#L160)) is the read side.
Nothing has ever assembled a `ProjectedGraph` from it.

### 1.1 `load_snapshot` — rebuild the projection from the ledger

[`lib.rs:1781`](../core_indexer/src/lib.rs#L1781)

Replace the `PyNotImplementedError` with a real read: `reconstruct("now")` →
group concepts by kind → rebuild `functions`/`classes`/`modules`/`imports`/
`constants` → replay the four edge kinds into the five reverse indexes.

The correctness bar is a **round-trip identity test**, and it must be the
strict one: `analyze(p)` then `load_snapshot()` in a *fresh interpreter* must
produce byte-identical entity dicts and identical traversal results at depth 3.
The v0.7 plan's third piece of cross-cutting test debt — "no parity test
between the two ingest paths" — is exactly the failure mode here, for a third
ingest path.

**Risk:** high. This is the one item in v0.8 that can silently produce a
*subtly different* graph rather than an obviously broken one. The parity test
is not optional and should be written before the implementation.

### 1.2 `export_snapshot` — decide whether it is still a thing

[`lib.rs:1772`](../core_indexer/src/lib.rs#L1772)

If 1.1 lands, the ledger *is* the snapshot and a separate serialized format is
a second source of truth with no consumer. **Recommendation: cut it** — delete
the pyfunction, the `coderadar export` command, and `CodeGraph.export_snapshot`,
the same call §3 and §4 of the v0.7 plan made for the config knobs and the
`mutations` command. Ship 1.1's `load_snapshot` as the whole story.

*If cut, `tests/test_cli.py::test_an_unimplemented_snapshot_export_is_not_a_success`
goes with it.*

### 1.3 Retire `_ensure_graph`'s re-index

[`cli.py`](../py_agent/src/coderadar/cli.py)

With 1.1, `_ensure_graph` becomes: try `graph_stats()`; on empty, `_activate` +
`load_snapshot`; only if the store is *absent or stale* fall back to
`analyze()`. Staleness is already computable — v0.7 6/C6 exposed `indexed_at`
for the MCP staleness banner.

The CLI tests from `acadb64` already pin the behaviour that matters
(`stats` answers, no "No graph loaded"), so this is a substitution under a
green test, which is the safe shape.

### 1.4 Measure it

Extend `tests/test_v1_gaps.py`'s real-repo benchmark with a cold-start leg:
`analyze` once, then time `load_snapshot` in a fresh process. Record the number
in this document. If it is not at least an order of magnitude under 46 s, 1.1
has not achieved its purpose and the design needs revisiting rather than
shipping.

## Phase 2 — Make the traversal surface whole

*Goal: close the three places where the graph knows more than the API will say.*

### 2.1 Route `explore()` through the Rust `traverse` binding

[`__init__.py`](../py_agent/src/coderadar/__init__.py) · `open-items.md` §1.1

`CodeGraph.explore` BFSes over `callers_of`/`callees_of` — one edge kind —
and since `b140cbf` honestly returns `[]` when asked for another. The Rust
`traverse` has handled all four kinds since the resolve backfill.

Delete the Python BFS; call `_core.traverse`. This is the same move
`traversal-matrix.md` step B made for `executor.py`, and it deletes code rather
than adding it.

Keep the honest-empty contract for kinds that genuinely have no data, and drop
`EDGE_KIND_CALLS` — it exists only to explain the limitation this task removes.

`explore` is one of the four primary MCP tools. The existing
`tests/test_explore_api.py` already asserts both halves (that a `calls` request
comes back non-empty, that an `imports` request currently comes back empty);
the second assertion inverts as part of this task, deliberately and visibly.

### 2.2 `as_of` upstream and bidirectional — implement or document permanently

[`lib.rs:1397`](../core_indexer/src/lib.rs#L1397) · `open-items.md` §2.2

Macrame's `TraversalBuilder` is out-edge-only, so `as_of` with
`direction in {"in", "both"}` raises. Two honest options:

- **Implement** — reconstruct the historical projection at `ts` (Phase 1.1
  gives exactly this machinery) and run the normal in-memory BFS, which is
  direction-agnostic. Phase 1 makes this nearly free, which is why it is
  sequenced after.
- **Document** — if not, say so in the README's temporal section and in the
  tool description, rather than only in a `NotImplementedError` an agent
  discovers by calling.

**Recommendation: implement, after Phase 1.** The cost drops from "new Macrame
traversal machinery" to "call the existing BFS against a reconstructed
projection".

### 2.3 `IMPLEMENTS` as a distinct edge kind

`open-items.md` §2.6

Nine edge types are declared in [`storage.rs:40`](../core_indexer/src/storage.rs#L40);
`ALL_EDGE_KINDS` is four. Interface implementation is currently folded into
`extends`, so `class C implements Serializable` and `class C extends Base` are
indistinguishable in a traversal — a real loss for Java, Go, TypeScript, and C#,
four of the twelve Tier-1 languages.

Scope this deliberately: it is a resolve-cascade change
(`resolve_class_hierarchy` must split its output), a persistence change, and a
`normalize_edge_kinds` change. It is the largest item in Phase 2 and the most
skippable — **defer to v0.9 if Phase 1 runs long.** The other six declared-but-
unused kinds (`REFERENCES`, `DECORATES`, `INSTANTIATES`, `CONTAINS`) have no
demonstrated demand and should stay unimplemented rather than be added for
symmetry.

## Phase 3 — Wire it or cut it, third pass

*Goal: apply the decision the v0.7 plan already made twice to the three things
that survived it.*

`open-items.md` §1.4. Each of these is imported by tests and by nothing else.
The v0.7 plan closed §3 (config) and §4 (dead code) with the same question and
the answer was "cut" both times; `acadb64` cut `mutations` on the same grounds.

| Item | Lines | Recommendation |
|---|---|---|
| `mutation/tool_router.py` | 215 | **Cut.** Named in v0.7 §4 and not resolved. Its live paths assume attribute access (`plan.id`, `result.status`) on what the FFI returns as **dicts** — so it would fail on first real use. Its tests only exercise the `graph=None` path, which is the exact pattern §3.2 of `open-items.md` describes. |
| `agent/` (`graphrag.QueryPlanner`) | ~300 | **Cut or wire.** No production path, no README claim backing it. If there is an intended future, say so in a module docstring and leave it; if not, delete. |
| `lsp/` (`pool.LSPPool`, `LSPOverride`, `ManagedServer`) | ~400 | **Keep — README downgraded to "planned" instead.** Resolved before the v0.7.0 tag; see below. |

The decision that mattered was `lsp/`, the only one of the three the README
sold to a user. **Resolved (2026-08-23, pre-v0.7.0):** the README's resolution
cascade row moved from "L5 · 1.00 · optional, disabled by default" to
"**Planned** — not wired into the cascade", with a note that L1–L4 are what
actually run. The code stays; the claim goes. That closes the honesty half of
this item at zero risk, and leaves wiring the override behind its config flag
as ordinary future work rather than a documentation debt.

`agent/` and `tool_router.py` remain open on the cut-or-wire question. Neither
is sold in the README, so neither is urgent.

## Phase 4 — Test the surfaces that still have the smoke-test property

*Goal: stop finding these one release at a time.*

Four smoke passes found four bug classes, and every one shared a shape:
**a surface that produced plausible output and exited 0, under a green suite.**
`open-items.md` §3.2 records the pattern. The remaining work is to find where
else it holds rather than wait for the next release check.

### 4.1 Complete the Tier-1 signature matrix

`open-items.md` §1.3. `tests/test_language_signatures.py` covers 10 of the 12
Tier-1 languages. **Add C and C#.** C is the priority: `93b82f9`'s root cause
was that C and C++ hang the parameter list off the declarator chain, and only
C++ is pinned.

While there: the file asserts parameters and keyword. It does not assert
**return types**, which is the other half of a signature and the site of the
TypeScript `-> : string` bug. Add a return-type column to `CASES`.

### 4.2 An ingest-parity property test

The v0.7 plan asked for this (`analyze` vs `update_file`) and it remains the
single highest-yield test in the codebase: 0.3, 0.3b, and 0.4b were all
copy-drift between ingest paths. Phase 1.1 adds a **third** path
(`load_snapshot`), so make it three-way:

```
analyze(p)                      ─┐
analyze(p) + update_file(each)  ─┼─→ identical entity dicts, identical traversals
analyze(p) → fresh → load()     ─┘
```

### 4.3 An audit for the remaining "plausible output, exit 0" surfaces

The four already found were: visualizers, CLI commands, MCP guidance strings,
and non-Python extraction. Candidates not yet swept, in rough order of how much
an agent trusts them:

- **MCP tool *descriptions*** — `d269768` checked guidance strings for tool
  names that do not exist. Nothing checks that a tool's description matches its
  parameters, or that its promises hold (e.g. `codegraph_search_similar`
  naming entity kinds that are actually embedded).
- **Framework resolvers** — the README claims 13. Each is a pattern matcher
  that returns "no match" indistinguishably from "not wired". Test that each
  named framework resolves at least one route on a fixture.
- **The query language** — the Pest grammar accepts field names; a query
  against a field that is never populated returns "No results", which is the
  same output as a correct query with no matches. `is_async` was in exactly
  this state until `b140cbf`. Enumerate the queryable fields and assert each
  can match something.
- **Smell rules** — golden-tested for 4 rules since v1 §3.1. The other rules
  have the `god-class` problem: covered by a test that never asserts the rule
  fires.

### 4.4 The CI question

`open-items.md` §3.1. clippy 100, ruff 785 (633 auto-fixable), fmt 444 — under
a job that is `continue-on-error: true` and has never been green.

**Recommendation, in this order:**

1. `cargo fmt --all` and `ruff check --fix` — mechanical, reviewable as a
   single no-behaviour-change commit, kills 444 + 633 of 1,329.
2. Triage the ~100 clippy and ~150 residual ruff findings. Some are real; most
   will be `#[allow]`/`# noqa` with a reason, or config-level opt-outs in
   `pyproject.toml` / `clippy.toml`.
3. **Then** flip `continue-on-error: false`, which was v0.7 §5.2's intent.

Do this **last** in the release, not first: a 1,300-line mechanical diff
landing before Phases 1–3 makes every one of those diffs harder to review, and
`git blame` worse for the code v0.8 actually changes.

## Phase 5 — Release engineering

### 5.1 CHANGELOG.md

`open-items.md` §1.5. The project ships to PyPI as `coderadar-rs`. Between
0.6.43 and 0.6.47 the CLI removed a command, changed three exit codes, and
turned visualizer fabrication into a hard failure — all user-visible, all
recorded only in commit messages.

Start at v0.7.0 and backfill the 0.6.4x line from the existing commit messages,
which are unusually detailed and already contain the material.

### 5.2 Document the interim states as interim

Two places currently read as design decisions but are waypoints:

- `_ensure_graph`'s re-index (until Phase 1.3).
- `explore`'s single-edge-kind walk (until Phase 2.1).

If Phase 1 or 2 slips out of v0.8, these need a line in the README saying so.
Shipping a limitation is fine; shipping it silently is what v0.7 spent itself
correcting.

## Sequencing

| Phase | Content | Effort | Risk if deferred |
|---|---|---|---|
| **1** | Cold start (1.1–1.4) | ~3 days | Every CLI command costs a full re-analysis |
| **2.1** | `explore` → Rust traverse | ~0.5 day | A primary MCP tool answers `[]` to 3 of 4 edge kinds |
| **2.2** | `as_of` upstream | ~1 day | The temporal claim has a documented hole |
| **3** | Wire-or-cut `lsp/`, `agent/`, `tool_router` | ~1 day | A README-documented feature has no caller |
| **4.1–4.2** | Tier-1 matrix + ingest parity | ~1 day | The next ingest path drifts like the last three |
| **4.3** | Plausible-output audit | ~2 days | The next release check finds a fifth bug class |
| **2.3** | `IMPLEMENTS` edges | ~2 days | Interfaces stay indistinguishable from inheritance |
| **4.4** | Lint backlog + blocking CI | ~1 day | The lint job stays decorative |
| **5** | CHANGELOG + interim docs | ~0.5 day | Consumers read commit messages |

**Suggested order: 1 → 2.1 → 4.1/4.2 → 3 → 2.2 → 4.3 → 2.3 → 4.4 → 5.**

Rationale for the two non-obvious placements:

- **4.1/4.2 immediately after 2.1**, not at the end — the parity test is the
  guard for Phase 1's third ingest path, and it is worth having *before* the
  code it guards is trusted. Writing it after 1.1 ships means writing a test to
  confirm what you already believe.
- **4.4 second-to-last** — a mechanical 1,300-item diff landing early makes
  every subsequent review and `git blame` worse.

### Minimum viable v0.8

If the release needs to be small: **1 → 2.1 → 5.1**. Cold start is the item
users feel, `explore` is the item agents feel, and the CHANGELOG is the item
that makes the first two legible. Everything else can wait for v0.9 without
anything becoming dishonest.

## Explicitly out of scope for v0.8

Carried from `open-items.md` §2, unchanged in status:

- **Arg-span indexing** for the `update_signature` call-site cascade — mitigated
  by the `unverified_sites` warning and v0.7 §0.1's span verification.
- **Smell-metric approximations** — substring cyclomatic, base/call CBO. Pinned
  by golden snapshots, so they are stable rather than drifting.
- **Full `tsconfig.json` / `pyproject.toml` path-map parsing** — the `@/` and
  `~/` conventions cover the common case.
- **Stack Graphs / L1 resolution** — deferred post-v1; placeholder module
  already deleted and the omission documented.
- **TypeScript throughput** — `performance-roadmap.md`, a separate programme.
- **SQLite PRAGMAs, string interning, columnar extraction** — high-risk,
  post-v1.
- **The five unused Macrame edge types** beyond `IMPLEMENTS` (`REFERENCES`,
  `DECORATES`, `INSTANTIATES`, `CONTAINS`) — no demonstrated demand. Adding
  them for symmetry is how the five dead reverse-index fields in
  `traversal-matrix.md` §0 came to exist in the first place.
