# v0.8 Phase 1 Design — Ledger-Backed Cold Start (`load_snapshot`)

Status: **design — pre-implementation** (write the tests in §11 first, then code).
Supersedes: the `load_snapshot` stub at `core_indexer/src/lib.rs:2001` and the
`CodeGraph.load` NotImplementedError at `py_agent/src/coderadar/__init__.py:763-771`.
Plan: `docs/v0.8-improvement-plan.md` items 1.1–1.4; successor consumer:
`docs/fossil-mcp-improvement-plan.md` §3.1 (Stage 0.3 analysis cache is keyed off the ledger
revision exposed by this work) and §13.2 (three-way ingest parity, gate G1).

## 1. Goal

A fresh process opens the persisted Macrame ledger and rebuilds the in-memory
`ProjectedGraph` **without re-parsing source**. The loaded graph must be indistinguishable
from a freshly analyzed one on every Python-visible surface: `search`/`find` entity dicts,
`graph_stats`, `traverse`/`callers_of`/`callees_of`. `coderadar init` stays the one full
analyze; every later command in a fresh process is a sub-second-ish load (benchmark gate in
§16).

Non-goals (stated to keep scope honest):

- **No embedding persistence.** `set_embedding`/`set_embeddings_bulk` are in-memory
  (`graph.embedding_cache`); nothing reaches the ledger. The parity contract therefore
  requires `has_embedding=false` on both legs. A vector store is v0.8 Phase 2.
- **No historical (`as_of`) traversal** of the in-memory graph — Phase 2.2. But the load
  mechanism (`reconstruct(ts)`) is exactly its foundation: swap the timestamp and the same
  code rebuilds a historical projection.
- **No `IMPLEMENTS` edges** — Phase 2.3.
- **No change to `resolve_all_calls`.** Raw per-call-site `Function.calls` are not persisted;
  the loaded graph gets its call indices from persisted *resolved* data instead. Scoped
  re-resolution after a load still works because `update_file` re-parses the one file it
  touches (see §13).

## 3. The parity contract (acceptance criterion)

**Python-facing entity dicts, byte-identical.** Not the full `ProjectedGraph` struct — many
fields (embeddings, raw `calls`, `setter_of`, `exports`, …) are never persisted and are not
exposed. What is exposed:

| Kind | Dict builder | Keys |
|---|---|---|
| module | `module_to_dict` (`lib.rs:191`) | id, name, kind, file_path, language (Debug str), parse_quality (Debug str), classes/functions/imports/constants/type_aliases (id lists), file_version, has_embedding, embedding_hash |
| class | `class_to_dict` (`lib.rs:210`) | id, name, grammar_kind, kind, parent_module, file_path (from id), parent_id, docstring, line, end_line, start_line, decorators, span_start/span_end, name_span_start/name_span_end, **bases (raw names)**, has_embedding, embedding_hash. (MRO is **not** in the dict; no methods key.) |
| function | `function_to_dict` (`lib.rs:242`) | id, name, kind (FunctionKind), parent_module, file_path (from id), parent_id, docstring, return_type, line, end_line, decorators, is_async, is_generator, span_start/span_end, name_span_start/name_span_end, has_embedding, embedding_hash, signature (from parameters + return_type + declaration keyword) |
| import | `import_to_dict` (`lib.rs:342`) | id, name (from `raw`), kind, line, start_line, name_span_start/name_span_end, has_embedding, embedding_hash. **Resolution and structured kind are NOT exposed.** |
| constant | `constant_to_dict` (`lib.rs:356`) | id, name, kind, annotation, span_start/span_end, has_embedding, embedding_hash |
| type_alias | `type_alias_to_dict` (`lib.rs:371`) | id, name, kind, target, span_start/span_end, has_embedding, embedding_hash |

Plus: `graph_stats` counts (`modules/classes/functions/imports/constants/type_aliases/
file_count/call_edges`), `traverse`/`callers_of`/`callees_of` outputs (depth-3 BFS over
CALLS/IMPORTS/EXTENDS/OVERRIDES; external ids are filtered by `entity_ref_to_dict` so they
never appear in output), and `index_edge_stats` counts.

**Three-way** (fossil plan §13.2, v0.8 §4.2): `analyze` ≡ `analyze + no-op update_file` ≡
`fresh process load_snapshot`. Any future projection consumer extends this harness with its
own invariant (e.g. centrality scores identical across the three legs).

**Comparison rules:**

- Enumerate per kind via `search_entities("", 100_000, kind)` — an empty query matches
  every entity (`name_lower.contains("")`).
- Canonicalize: sort entity lists by id, JSON with sorted keys. Compare A vs C (load) and
  A vs B (update) byte-for-byte after normalization.
- `indexed_at` is **excluded** (leg A = commit time, leg C = load time); `indexed_root`
  compared when a root is supplied.
- Embedding fields must be `false`/empty on **both** legs (in-memory-only embeddings).
- `call_edges` and `index_edge_stats` compared exactly (they're computed from the same
  rebuilt indices).
- Module membership lists (`classes`/`functions`/… in the module dict) must preserve
  fresh-analyze **extraction order** → persist them explicitly in module JSON (§5).

**Why the ledger alone suffices for depth-3 traverse parity:** all edge kinds Python can
traverse are either (a) rebuilt by re-running the deterministic resolution cascade on
persisted entity data (IMPORTS, EXTENDS, OVERRIDES), or (b) read directly from persisted
resolved call data (CALLS incl. synthetic-kind edges, §7). `CONTAINS`/`REFERENCES`/
`DECORATES`/`INSTANTIATES` are never persisted and never traversed (`ALL_EDGE_KINDS`,
`lib.rs:1382`).

## 5. Concept JSON v2 (the schema change)

Current `entity_meta` (`storage.rs:403`) already stores: common `kind`, `file_path`
(module id prefix), `line`, `exit_line`, `docstring`, `decorators`, `content_hash` (body
hash, hex, entity-specific), `embeddings`; module: `name`, `language`, `classes`,
`functions`, `imports`, `constants`, `type_aliases` (id lists).

**v2 changes are additive.** Write side: `entity_meta` (used by `analyze`'s
`upsert_concepts_bulk` and `update_file`'s `persist_entities` — one function, so both paths
get v2 for free). Read side: `load_snapshot`.

Add to **all** entities:

```text
"meta_version": 2          // v1 stores have no meta_version → load rejects cleanly (§12)
"name": <String>           // explicit; title is not a safe source (import title = "__import__")
```

Per kind (serde where noted; `serde = { features = ["derive"] }` is already in Cargo):

```text
function:
  "fn_kind": FunctionKind            // serde: Free|Method|StaticMethod|ClassMethod|Property|
                                     // PropertySetter|PropertyDeleter|CachedProperty|
                                     // AbstractMethod|DataclassSynthesized{from_class}
  "parameters": [Parameter]           // name, annotation, default_value, is_varargs, is_kwargs,
                                     // is_positional_only, is_keyword_only
  "parent_class": EntityId | null
  "resolved_calls": [ResolvedCall]    // serde: Function{id} | Method{receiver, method} |
                                     // Constructor{id} | Builtin{name} | External{name} |
                                     // Unresolved{reason, raw}
  "is_generator": bool
  "source": "impl" | "stub"           // SourceType
  "metrics": { cyclomatic, nesting_depth, return_count }
  "signature_hash": u64 (hex string)  // body hash already present as "content_hash"
class:
  "parent_class": EntityId | null
  "bases": [UnresolvedRef]            // name, path, line, col
  "is_type_checking_only": bool
  "fields": [Field]                   // name, annotation, source, default_value, is_class_var,
                                     // span, name_span
  "content_hash": u64 (hex)
import:
  "import_kind": { "variant": "ModuleImport|FromImport|RelativeImport|StarImport|Side",
                   "module": ..., "alias": ..., "names": [[name, alias|null], ...],
                   "level": n }       // tagged representation; enough to rebuild ImportKind
                                     // (incl. RelativeImport { level, module, names }) without
                                     // re-parsing `raw`
  "is_type_only": bool
  "name_span": [start, end]
constant:
  "annotation": String | null
  "default_value": String | null
  "source": "impl" | "stub"
  "span": [start, end]
  "name_span": [start, end]
type_alias:
  "target": String
  "source": "impl" | "stub"
  "span": [start, end]
  "name_span": [start, end]
module:
  "name": String                      // explicit (already present — keep)
  "parse_quality": "Clean"|"Partial"|"Tainted"|"Deferred"
  "file_version": 1
  "content_hash": u64 (hex)
  // membership lists already present in v1 — keep as the canonical ORDERED lists
```

`Function.calls` (raw UnresolvedRef call sites) are **not** persisted (decision, §13).
`Class.effective`, `Module.exports`/`package`, `Function.setter_of`, embeddings: not
persisted (no readers / in-memory only).

**Serde derives to add** in `types.rs`: `ByteSpan`, `Parameter`, `UnresolvedRef`,
`FunctionKind`, `ResolvedCall`, `ReceiverShape`, `UnresolvedReason`, `SourceType`, `Field`
(all `#[derive(Serialize, Deserialize)]`); `ImportKind` via a small hand-written
`impl` or a tagged helper struct (its tuple-variant `names: Vec<(String, Option<String>)>`
serializes as arrays of 2-arrays — fine). `Language`/`ParseQuality` stay as lowercase/Debug
**string** round-trips through small `from_str` parsers (they already appear in JSON as
Debug strings via `module_to_dict`).

**One-time migration cost:** the JSON change alters nothing about the ledger schema
(content is an opaque blob in macrame `concepts.content`), but it changes what `update_file`
writes for changed files; a full `analyze` after upgrade rewrites every concept with v2
JSON (new open intervals). Old v1 stores are **not** loadable (§12).

## 6. `load_snapshot` algorithm (new pyfunction)

Signature: `load_snapshot(db_path: &str, root: Option<&str>) -> PyResult<PyObject>`
(replaces the stub at `lib.rs:2001`). Returns a dict:
`{ modules, classes, functions, imports, constants, type_aliases, files, call_edges,
revision (i64 seq_anchor), predates_recorded_history (bool), indexed_at, indexed_root }`.

Steps (in `py.allow_threads`):

1. `store = CodeGraphStore::open(db_path)` (`storage.rs:98`).
2. `state = store.reconstruct(&now_iso8601())` — a canonical
   `YYYY-MM-DDTHH:MM:SS.ffffffZ` timestamp (UTC, µs), generated with the same
   `now_iso8601()` helper every persistence path uses (`storage.rs:61`). Not the magic
   string `"now"`: `reconstruct` runs its argument through `timestamp::normalize`
   (macrame-db `src/util/timestamp.rs:78`), which accepts **only** canonical form and
   rejects `"now"` — a generated timestamp also records exactly when the snapshot was
   materialized.
3. If `state.predates_recorded_history`: record a warning in the outcome (load proceeds).
4. **Parse concepts.** For each `NodeAttributes` in `state.concepts`: parse `content` JSON;
   require `meta_version == 2` — if any concept lacks it, **hard error**
   `"concept <id> predates concept-JSON v2 (no meta_version); re-run coderadar analyze to
   upgrade the store (N of M concepts affected)"`. Never silently load a degraded graph
   (plan 1.1 doctrine; a partial snapshot that answers queries with gaps is the enemy).
   Group by `kind` string.
5. **Build entity maps** (fresh `ProjectedGraph`, `CodeGraph::new(config)`):
   - module → `Module { path: PathBuf::from(file_path), language: Language::from_json,
     parse_quality: ParseQuality::from_json, file_version (JSON, expect 1),
     package: None, exports: vec![], star_exports: None, membership lists: JSON order,
     content_hash, embedding: default }`
   - class → `Class { …JSON…, resolved_bases: vec![], mro: vec![], mro_error: false,
     methods: vec![], effective: EffectiveClass::Plain, source: default, embedding: default }`
   - function → `Function { …JSON…, calls: vec![], resolved_calls: JSON, setter_of: None,
     embedding: default }`
   - import → `Import { raw: JSON, kind: ImportKind::from_json (structured),
     resolution: Unresolved, line, is_type_only, name_span, embedding: default }`
   - constant / type_alias → from JSON.
   - `file_to_modules`: derive `file_path → [module.id]` (insertion order = concept order;
     single module per file in practice).
   - `module_by_dotted_name`: empty (verified never populated, §2).
6. **Run the resolution cascade** — same functions, same order as `analyze` (`lib.rs:747-751`),
   minus `resolve_all_calls` (line 752):
   `resolve_imports → populate_class_methods → compute_all_mro → resolve_class_hierarchy →
   resolve_overrides`. All are pure rebuilds over the projection (each clears its own output
   indices; `resolve_imports` clears `importers` and rebuilds `imports_by_importer` from
   `module.imports` — safe from an empty projection). Note for the implementer:
   `resolve_imports` does **not** pre-clear `imports_by_importer` — irrelevant on a fresh
   projection, do not "fix" it here.
7. **Rebuild call indices** from data, not from re-resolution (§7).
8. Attach the store (`with_store`, `mod.rs`) — the loaded graph keeps the ledger attached
   (temporal tools + Stage 0.3 revision keying); `has_store()` then reports true, so
   temporal queries work on loaded graphs.
9. `graph.commit_projection(proj)`; set `GLOBAL_GRAPH` and `INDEXED_ROOT` (canonicalized
   `root` when supplied, else leave root unset and record that in the outcome).
10. `indexed_at`: db file mtime (unix seconds) — same source the CLI staleness banner
    reads; the ledger's `seq_anchor` is exposed as `revision`.

The whole load is one `Arc<CodeGraph>` swap — `with_graph` readers see either the old or
the new graph, never a half-built one (same pattern as `analyze`).

## 7. Edge → index reconstruction

| Ledger edge kind | In-memory home | Rebuilt how |
|---|---|---|
| CALLS | `callees_by_caller` + `callers_by_callee` | from **restored `resolved_calls`**, mirroring `resolve_one_function`'s pair build (`resolve_calls.rs:106-125`, applied at 358-377): `Function(id)`/`Constructor(id)` → id; `Method{receiver, method}` → method; `Builtin(name)`/`External(name)` → `external::{name}` pseudo-target; `Unresolved` → nothing. Both directions, `BTreeSet` insert (dedup). **Ledger CALLS edges are NOT a valid source here**: `persist_edges` skips `external::`/`builtins.` callees (`persistence.rs:74-77`), so the ledger alone would under-reconstruct the in-memory indices that fresh analyze keeps. |
| ROUTE, MIDDLEWARE, DEPENDENCY, HANDLES, USES, INJECTS, REGISTERS, DEPENDS_ON, NAVIGATION, CALLBACK (framework synthetics) | same CALLS indices | from ledger edges directly: any kind **not** in {IMPORTS, EXTENDS, OVERRIDES} → caller→callee into both call indices, deduped. These kinds never appear in `resolved_calls`, so no double-count. |
| IMPORTS | `importers` + `imports_by_importer` | **not** read from edges — `resolve_imports` rebuilds them deterministically from `module.imports` + `find_module_by_dotted_name` over the restored modules (same inputs as analyze → same outputs). |
| EXTENDS | `subclasses` + `Class.resolved_bases` | `resolve_class_hierarchy` rebuilds from restored `Class.bases` (same rule: same-module + global-unique). |
| OVERRIDES | `overrides_base` + `overridden_by` | `resolve_overrides` rebuilds from restored MRO + methods. |

**Single source per family:** real calls come only from `resolved_calls`; synthetic-kind
edges only from the ledger. This keeps `resolved_calls` and the call indices
mutually consistent by construction, and means a `CALLS` ledger edge that duplicates a
`resolved_calls` pair (can happen: `persist_edges_scoped` writes CALLS from the index,
which includes synthetics) is ignored on load.

External/builtin pseudo-targets (`external::…`) are kept in the indices (fresh analyze keeps
them too — `callers_of`/`callees_of`/`traverse` filter them at the dict boundary via
`entity_ref_to_dict` returning `None`), so index counts and traversal behavior match.

## 8. Why the cascade is safe to re-run on a loaded projection

Every cascade function is a deterministic rebuild from entity data that is fully persisted
(§4): `resolve_imports` (Import.kind + module ids + path suffix matching),
`populate_class_methods` (Function.parent_class), `compute_all_mro` (Class.resolved_bases),
`resolve_class_hierarchy` (Class.bases), `resolve_overrides` (MRO + method names). None
touch `Function.calls`, `resolved_calls`, or the call indices, and none depend on
embeddings. Running them in the exact `analyze` order guarantees the same intermediate
states (`Class.methods` before `resolve_overrides`, `mro` before both) that the in-memory
pipeline produces.

`resolve_all_calls` is the one function that **cannot** re-run (it needs raw call sites),
which is exactly why `resolved_calls` is persisted and the indices are rebuilt in §7
instead.

## 9. CLI activation path (retire `_ensure_graph` re-analysis, item 1.3)

`_ensure_graph(path)` becomes:

1. `_activate(path)` — loads `.coderadar.toml` into the Rust process config (already done;
   this also lands BUGS_QUIRKS #3: the effective config for every command is the one in the
   project, not a process-lifetime stale one).
2. Resolve the db path the same way Rust does (`store_path_for(root, config.database)`:
   absolute paths as-is, else root-relative; default `.coderadar/store/coderadar.db` —
   `cli.py:212`, `storage.rs` path helper).
3. **Staleness check** (cheap heuristic, no content hashing): if the store exists and no
   indexable source file under root has mtime newer than the store `.db` mtime (2s grace),
   the store is fresh.
4. Fresh → `coderadar.load(db_path, root)` (→ `load_snapshot`); stale or absent →
   `coderadar.analyze(root)` (full re-index; for an initialized project the store attaches
   automatically via parent-dir-exists, `lib.rs:528-560`, so the re-index persists).
5. Any `load` error (v1 store, corrupt db, …) → log the reason and fall back to
   `analyze` (this is also the v1→v2 store upgrade path, §12).

Behavioral notes:

- `coderadar init` is unchanged (writes `.coderadar.toml`, `analyze(create_store=True)`).
- `coderadar analyze` (explicit command) always does a full analyze — it's the
  re-indexing command, not the activation path.
- `coderadar load-snapshot <path>` keeps working and becomes real (it already calls
  `coderadar.load`).
- One-shot MCP server (`--no-daemon`) inherits the same `_ensure_graph`, so MCP cold starts
  get the ledger path too.

## 10. Python API changes

- `CodeGraph.load(db_path, root=None)` (`__init__.py:763`): remove the
  NotImplementedError; call `_core.load_snapshot(db_path, root)`, then re-run the
  **same** star-export pass `analyze()` runs (extract `__all__` via
  `extract_all_exports`, apply with `set_module_star_exports_bulk`) — shared helper
  `_apply_star_exports(root)`. Rationale: `star_exports` is in-memory only, so a loaded
  graph would otherwise miss it and scoped re-resolution of wildcard imports after a load
  would silently under-resolve versus the analyze flow. Cost: one rglob over `*.py`.
- `CodeGraph.export_snapshot` (`__init__.py:626`): **remove** (item 1.2). Remove the Rust
  `export_snapshot` pyfunction stub (`lib.rs:1992`) and the
  `test_an_unimplemented_snapshot_export_is_not_a_success` test. A snapshot is the store;
  the command was a misnomer that exits 0 with plausible-looking failure output — exactly
  the surface class this program exists to kill.

## 12. Migration and compatibility

- **v1 stores** (pre-upgrade): concept JSON lacks `meta_version` → load hard-errors with
  the count of affected concepts; CLI falls back to `analyze`, which rewrites all concepts
  v2 (one-time). No silent degradation.
- **Mixed stores cannot occur**: a full `analyze` re-upserts *all* concepts; `update_file`
  after a full v2 analyze only writes v2. The only mixed state is pre-upgrade stores,
  handled above.
- **Ledger growth**: every analyze opens new intervals for all concepts (existing
  behavior — `upsert_concepts` upserts by id, closing prior intervals). v2 JSON is larger
  per concept (parameters, fields, resolved_calls). Expect concept rows to grow ~2-5×;
  `reconstruct` cost is O(open concepts + open edges), not history. Benchmark in §16; if
  `reconstruct` becomes the bottleneck, macrame has `reconstruct_incremental`
  (`replay.rs:197`) as a follow-up (not in P1).
- **Edge integrity**: single-open-interval guard + retire-before-assert means
  `reconstruct` returns ≤1 open interval per `(src, dst, kind)`; triple-dedup in §7 is
  defensive only.

## 13. Known limitations (documented, not defects, in P1)

- **Loaded `Function.calls` is empty.** Raw call sites are parse-time data and not
  persisted. Consequence: *scoped* re-resolution (`update_file`, `remove_file`) works
  correctly on a loaded graph — the touched file is re-parsed (fresh `calls`), other
  files' *resolved* state comes from the restored indices/`resolved_calls`. But anything
  needing whole-graph raw call data (a full `resolve_all_calls` re-run) cannot run from a
  load; that's by design — the resolved data *is* the persistence boundary.
- **`resolved_calls`-dependent analytics** (smells scoring, dead code, RTA-lite,
  centrality) get fully restored data via v2 JSON — so they work on loaded graphs **for
  the persisted repo state**. (This is what fossil §7.3 calls "rebuild lazily after a cold
  load_snapshot": here the rebuild is a plain restore, cheaper than the lazy design they
  sketched, because the resolved data is persisted.)
- **Embeddings absent** (in-memory only; §1).
- **`indexed_at` after load = db mtime**, not the exact last commit time (the ledger's
  recorded history holds it, but `MaterializedState` doesn't surface it; using mtime keeps
  the staleness banner honest: it's when the store was last written).
- **Star exports re-derived by the Python wrapper** (§10), not from the ledger — they're
  source-derived and cheap; persisting them would duplicate the source.

## 14. Out of scope (P2)

Historical traversal (`reconstruct(ts)` with arbitrary ts → as-of projection; the load
code is the skeleton), vector store for embeddings, `IMPLEMENTS` edges, incremental
`reconstruct`, multi-root/multi-store graphs, snapshot *export* to a portable artifact
(distinct from the store; if ever wanted, it's a new surface with its own design).

## 18. Post-implementation notes (2026-07-29)

Three deviations from this design, all found during implementation:

1. **`module_by_dotted_name` was a dead index.** No code path ever populated the
   `ProjectedGraph.module_by_dotted_name` field this design proposed filling, so
   the O(1) lookup in §6 could not exist. Implemented instead:
   `module_path_index: HashMap<segment-boundary suffix → module id>`
   (`rebuild_module_path_index`, rebuilt after every analyze cascade, cold load,
   `update_file`, `index_file`, and `remove_file`). `find_module_by_dotted_name`
   now does a longest-suffix hash lookup; a miss returns `None` directly because a
   built index is *complete* (the legacy full scan is retained only for graphs
   whose index is empty, i.e. hand-built unit-test projections). Effect:
   `resolve_imports` 7.28s → 0.003s on the 605-file repo; fresh analyze
   46.2s → 13.6s.
2. **Ledger edge persistence had a silent total-failure mode.** The call resolver's
   symbolic heuristic targets (capitalized receiver → pseudo-target
   `Date::now`, `Math::max`, …) have no concept row, and the FK check in
   `persist_edges_scoped` only knew the `external::`/`builtins.` prefixes. Each
   all-or-nothing batch containing one such edge aborted with FOREIGN KEY and was
   swallowed by `let _ =` — producing stores with complete concepts and **zero**
   edges. Fixed: an edge is asserted only if **both** endpoints are entities of
   the projection (the exact set the concept flush just wrote). Symbolic
   heuristic targets stay in the in-memory call indices (design §3: derived
   state is in-memory); the ledger holds FK-safe edges only. The `persist_edges`
   error at the analyze call site is now surfaced on stderr instead of dropped.
3. **No-op `update_file` duplicated module imports** — the `apply_diff_update`
   removal sets (`old_imports`, `old_classes`, `old_constants`, `old_aliases`)
   were keyed by raw (Windows-backslash) stored IDs while lookups normalized to
   slashes, so every unchanged entity looked new and was re-inserted. All
   `old_*` sets are now keyed by normalized ID (removal maps back via
   `canonical()`), matching the `old_hashes` fix that preceded this round.
   Verified: no-op rewrite → `entities_added: 0`, imports unchanged.

Also (test-side, no product change): `tests/test_v1_gaps.py` as-of timestamps now
use real microseconds (`%f`); a second-truncated "now" captured after the write
could sort before a microsecond-precision `valid_from` and flake the test.
