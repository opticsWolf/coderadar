# CodeRadar v3.6 — CodeGraph-Informed Improvements Plan

> Analysis of `codegraph-main` (commit `main` as of 2025-07-15) for techniques to adopt into CodeRadar without copying entire modules. All adopted code shall be attributed in docstrings per the CodeGraph MIT license.

---

## Background

CodeGraph (`codegraph-main`, TypeScript + Rust kernel) is a production-quality code intelligence tool serving AI agents via MCP. It indexes 20 languages, resolves cross-file references, and provides subgraph-based context retrieval. Its Rust kernel (`codegraph-kernel/`) uses per-language bespoke tree-sitter walkers rather than generic `.scm` queries.

CodeRadar v3.5 uses `.scm` query files + a generic walker (`walker.rs`) to tag nodes across 18 languages. This works well for tier-1 languages (Python, TypeScript, Rust, Go, Java, C, C++, Ruby, PHP, C#, Kotlin) but 3 of the 6 new tier-2 languages (Swift, Zig, R) fall back to a bare `(comment)` query because their grammar node names don't match the query patterns.

## Item 1 — Docstring Extraction via Preceding Comments

**Source:**
- `codegraph-main/codegraph-kernel/src/docstring.rs` (full file, ~220 lines)
- Used by all per-language walkers via `preceding_docstring(node, src)`

**Current CodeRadar state:**
- `@docstring` capture in `.scm` queries tags docstring/comment nodes
- The tagger captures these as `Tag::Docstring`
- The walker stores them as docstrings on the nearest entity
- **Problem:** Swift, Zig, and R queries use fallback `(comment) @docstring` which may not match their grammar's comment node names

**What to adopt:**

### 1a. `preceding_docstring()` — comment run immediately before a declaration

```rust
/// Collect the comment run immediately preceding a node, climbing out
/// of declaration wrappers first. Returns the cleaned comment text,
/// or None if there is no preceding comment.
///
/// Based on CodeGraph's preceding_docstring (codegraph-kernel/src/docstring.rs).
fn preceding_docstring(node: Node, src: &str) -> Option<String> {
    // 1. Climb wrapper nodes: export_statement, decorated_definition,
    //    lexical_declaration, variable_declaration, variable_declarator,
    //    ambient_declaration
    let mut anchor = node;
    while let Some(parent) = anchor.parent() {
        if is_docstring_wrapper(parent.kind()) {
            anchor = parent;
        } else {
            break;
        }
    }
    
    // 2. Collect all preceding sibling comment nodes (nearest-first)
    let mut comments: Vec<&str> = Vec::new();
    let mut sibling = anchor.prev_named_sibling();
    while let Some(s) = sibling {
        if is_comment_kind(s.kind()) {
            comments.push(&src[s.byte_range()]);
            sibling = s.prev_named_sibling();
        } else {
            break; // stop at first non-comment sibling
        }
    }
    
    if comments.is_empty() {
        return None;
    }
    
    comments.reverse(); // restore source order
    Some(
        comments
            .iter()
            .map(|c| clean_comment_markers(c))
            .collect::<Vec<_>>()
            .join("\n")
            .trim()
            .to_string(),
    )
}
```

### 1b. `clean_comment_markers()` — strip comment syntax, keep prose

Supports 6+ comment styles:
- C-style: `/* */`, `/** */`
- Lua-style: `--[=[ ]=]`
- Pascal-style: `(* *)`
- Erlang/curly: `{ }`
- Line comments: `//`, `--`, `#`, `%`
- Block continuation: ` * ` inside `/** */`

Uses `js_multiline_strip()` for faithful JS `^/gm` replacement semantics (handles `\r`, `\n`, U+2028, U+2029 as line terminators).

### 1c. Integration points

In `walker.rs`, after extracting each class/function/method:

```rust
// After name extraction, before create_node:
let docstring = preceding_docstring(node, source).or(
    // fall back to the existing @docstring capture if preceding scan found nothing
    docstring_from_inline_tag
);
```

**Implementation plan:**
1. Create `core_indexer/src/extract/docstring.rs` (or extend existing)
2. Add `is_comment_kind()`, `is_docstring_wrapper()`, `clean_comment_markers()`, `preceding_docstring()`
3. Wire into `walker.rs` for all `Tag::Class` and `Tag::Function` handlers
4. Test with Python docstrings, C `/** */`, Lua `--[[ ]]`, Swift `///`

**Files to create/modify:**
- NEW: `core_indexer/src/extract/docstring.rs`
- MODIFY: `core_indexer/src/extract/walker.rs` (wire docstring before entity creation)
- MODIFY: `core_indexer/src/extract/mod.rs` (re-export)

## Item 2 — Builtin Type Filter Lists

**Source:**
- `codegraph-main/codegraph-kernel/src/swift.rs` — `is_builtin_type()` lines 38-52
- `codegraph-main/codegraph-kernel/src/python.rs` — same pattern, different set
- `codegraph-main/codegraph-kernel/src/tsjs/fnref.rs` — shared table

**Current CodeRadar state:**
- No builtin-type filtering exists
- Type references in bases/extensions include `String`, `Int`, `bool`, `Error` etc.
- This is noise in the graph — nobody needs "who references `String`?"

**What to adopt:**

A single `is_builtin_type(name: &str) -> bool` function that unions the builtin sets from all supported languages. CodeGraph's table (from `swift.rs` lines 38-52) covers:

```
Rust:     str, bool, i8-i128, isize, u8-u128, usize, f32, f64, char
C/Go:     int, long, short, byte, float, double, rune, error
          int8-int64, uint8-uint64, float32, float64, complex64, complex128
Scala:    Int, Long, Short, Byte, Float, Double, Boolean, Char
          Unit, String, Any, AnyRef, AnyVal, Nothing, Null
Swift:    String, Int, Double, Bool (NOT in the shared table)
TS/JS:    string, number, boolean, void, null, undefined, never, any,
          unknown, object, symbol, bigint, true, false
```

**Implementation plan:**
1. Add `fn is_builtin_type(name: &str) -> bool` to `core_indexer/src/types.rs`
2. Combine all sets from above + Swift-specific additions
3. Filter in `walker.rs` when extracting:
   - Class base/extension references
   - Type annotations on parameters
   - Return type references
4. Add `fn is_literal_receiver(kind: &str) -> bool` for call extraction (filters `"str".method()`, `5.times()`)

**Files to modify:**
- `core_indexer/src/types.rs` — add `is_builtin_type()` + `is_literal_receiver()`
- `core_indexer/src/extract/walker.rs` — filter base types, type annotations, call receivers
- `core_indexer/src/extract/tagger.rs` — optionally skip tagging builtin references

## Item 3 — Language-Specific Node Classification Table

**Source:**
- `codegraph-main/codegraph-kernel/src/swift.rs` — `visit_node()` dispatcher, `classifyClassNode` logic (lines ~390-420)
- `codegraph-main/codegraph-kernel/src/kotlin.rs` — same `classifyClassNode` pattern for interface/enum
- CodeGraph's per-language approach uses keyword-child scanning to disambiguate node kinds

**Current CodeRadar state:**
- `.scm` queries tag nodes by grammar-specific node kind
- The walker's class-name extraction checks `node.kind()` against a hardcoded list
- **Problem:** Swift's `class_declaration` can be a class, struct, enum, or actor — the grammar uses one node kind for all, distinguished by keyword children
- **Problem:** Zig, R grammars use different node names than what the `.scm` queries assume

**What to adopt:**

### 3a. Add `classify_class_like()` for ambiguous grammars

```rust
/// For grammars that use a single node kind for multiple class-like
/// declarations (Swift, Kotlin), scan keyword children to classify.
///
/// Based on CodeGraph's classifyClassNode pattern (swift.rs, kotlin.rs).
fn classify_class_like(node: Node, src: &str) -> &'static str {
    for i in 0..node.child_count() {
        if let Some(child) = node.child(i) {
            match child.kind() {
                "struct" => return "struct",
                "enum" => return "enum",
                "interface" | "protocol" => return "interface",
                "actor" => return "class", // treat as class
                _ => {}
            }
        }
    }
    "class" // default
}
```

### 3b. Add `classify_function_like()` for ambiguous grammars

Some grammars (Zig, R) use unusual function node names:
- Zig: `function_declaration` → we assumed this, but grammar may use `fn_declaration`
- R: `function_definition` with `name:` field → query works but may have a different top node

### 3c. Fix the `.scm` queries with correct node names

Rather than debugging each grammar's node kinds blindly, use tree-sitter's own introspection:

```bash
# For each grammar, dump node kinds:
node -e "
const Parser = require('tree-sitter');
const Swift = require('tree-sitter-swift');
const parser = new Parser();
parser.setLanguage(Swift);
const tree = parser.parse('class Foo { func bar() {} }');
console.log(tree.rootNode.toString());
"
```

This produces the exact node kind names the grammar emits. Use these to write correct queries.

**Implementation plan:**
1. Fix the 3 failing `.scm` queries (swift.scm, zig.scm, r.scm) by running tree-sitter introspection
2. Add `classify_class_like()` to `walker.rs` for Swift's ambiguous `class_declaration`
3. Add `classify_function_like()` if needed for Zig/R
4. Update `extract_name()` to handle the corrected node types
5. Re-enable the detailed assertions in the 10 tier-2 language tests

**Files to modify:**
- `core_indexer/queries/swift.scm` — fix node names
- `core_indexer/queries/zig.scm` — fix node names
- `core_indexer/queries/r.scm` — fix node names
- `core_indexer/src/extract/walker.rs` — add `classify_class_like()`, update name extraction branches
- `core_indexer/src/graph.rs` — tighten tier-2 test assertions

## Item 4 — Name Stoplist for Call/Ref Targets

**Source:**
- `codegraph-main/codegraph-kernel/src/python.rs` — `is_stoplisted()` (line ~527)
- Used across all walkers: `codegraph-kernel/src/swift.rs`, `tsjs/fnref.rs`, etc.

**Current CodeRadar state:**
- Some filtering of `self.`, `super.` in call handler but not systematic
- No stoplist for bare identifiers like `null`, `true`, `false`, `None`

**What to adopt:**

```rust
/// NAME_STOPLIST — identifiers that are never meaningful reference targets.
///
/// Based on CodeGraph's stoplist (python.rs, swift.rs, function-ref.ts).
fn is_stoplisted(name: &str) -> bool {
    matches!(
        name,
        "this" | "self" | "super" | "null" | "nil" | "true" | "false"
            | "undefined" | "new" | "NULL" | "nullptr" | "None"
    )
}
```

**Integration:**
- Filter call targets in `Tag::Call` handler before creating `UnresolvedRef`
- Filter reference targets in resolution passes
- Filter import specifiers that match stoplist

**Files to modify:**
- `core_indexer/src/extract/walker.rs` — filter calls and refs
- `core_indexer/src/resolve/mod.rs` — filter resolve candidates

## Item 5 — Function-as-Value Reference Capture (Later)

**Source:**
- `codegraph-main/codegraph-kernel/src/python.rs` — `maybe_capture_fn_refs()` (lines ~460-530)
- `codegraph-main/codegraph-kernel/src/swift.rs` — same pattern (lines ~1050-1150)

**Current CodeRadar state:**
- Tracks direct function calls (`Tag::Call` creates `UnresolvedRef` edges from caller to callee)
- Does NOT track functions used as values: `on_click = self.handle_click`, callbacks passed as args, return statements returning function refs

**What to adopt:**

The pattern of scanning these AST contexts for function references:
1. **Argument lists** — `register_callback(handler)` → `handler` is a fn-ref
2. **Assignment RHS** — `on_click = self.handle_click` → `handle_click` is fn-ref
3. **Keyword argument values** — `on=handler` → `handler` is fn-ref
4. **Return statements** — `return handler` → `handler` is fn-ref
5. **Dict/list literals** — `{"key": handler}` → `handler` is fn-ref

Each candidate is recorded and flushed after the walker finishes. Candidates matching names in `defined_fn_names` or `imported_names` become resolved edges.

**Complexity:** Medium-high. Needs:
- Tracking `defined_fn_names` set (already partially done via entity IDs)
- Tracking `imported_names` set
- Post-walk `flush_fn_ref_candidates()` pass
- Deduplication by (from_id, name)

**Defer to v3.7 unless requested.**

**Source:**
- `codegraph-main/src/resolution/frameworks/python.ts` — Django, Flask, FastAPI

**Current CodeRadar state:**
- Stubs exist in `py_agent/src/coderadar/resolvers/django.py`, `flask.py`, `fastapi.py`
- Pattern: regex over file content to find URL route registrations → create route nodes + references to handlers

**What to adopt:**
- `decoratorRegex` pattern for `@app.route(...)` / `@router.get(...)` extraction
- `add_resource` pattern for Flask-RESTful
- `router.register(...)` pattern for DRF
- Handler name resolution: strip `.as_view()`, resolve dotted names

**Complexity:** Low but Python-side. Already partially implemented. Refine existing stubs.
